# Setting up your gateway

The whole path, from nothing to an agent reading your life. Budget ten minutes for the gateway itself; each source you connect adds a few more, and the ones that need you to register an app with a provider are the slow part.

If you are an agent doing this on someone's behalf, read [`../AGENTS.md`](../AGENTS.md) instead — it is this same path expressed as a contract, with every step marked human-required or automatable.

## 1. Run it

You need Docker, and a `.env` file with exactly one line in it. No Node install, no other configuration.

```bash
echo "POSTGRES_PASSWORD=$(openssl rand -hex 24)" > .env
docker compose up -d
```

The compose file pulls the published image, starts Postgres, applies migrations, and serves the gateway plus the Console from one origin. Every port is published on `127.0.0.1` only.

**Write the password to `.env`; do not put it in front of the command.** Compose reads `.env` for every subcommand, and Postgres bakes the value into its data directory on first boot. An inline `POSTGRES_PASSWORD=… docker compose up` generates a fresh password each time you run it: the second `up` cannot authenticate against the database the first one created, and every other compose subcommand fails on the missing variable before it does anything at all.

- **Console:** <http://localhost:8787> — on the gateway machine itself. Running the gate on a headless box (a Mac mini in a closet, a home server)? The Console deliberately never leaves that machine — so from your laptop, tunnel loopback over SSH and browse the same address locally:

  ```bash
  ssh -N -L 127.0.0.1:8787:127.0.0.1:8787 <your-box>   # leave it running, then open http://localhost:8787 here
  ```

  That is the supported way in from another device — the tunnel arrives on the box *as* loopback, encrypted and authenticated by your SSH key. Don't bind the port to the LAN or serve it over a tunnel service instead: the owner's surface answering only on loopback **is** the security model, not a limitation (§ Remote access has the full story).
- **MCP edge for agents:** `http://127.0.0.1:8788/mcp` (bearer-gated — nothing reaches it without a key)
- **Health:** `curl -s localhost:8787/healthz` → `{"status":"ok"}`

Do not lose that `.env` line. Postgres only honours the password on **first** boot — it initialises the data directory — so changing it later against an existing volume points the app at a role that does not exist rather than renaming anything. Keep it alphanumeric too: it is substituted into a connection URL as literal text, and a `/`, `:`, `@`, `?`, `#` or `&` produces a URL that parses wrong. `openssl rand -hex 24` cannot produce one; `openssl rand -base64 32` frequently does.

**Two ports, and they are knobs.** `REST_PORT` (8787) is the Console and the admin surface. `MCP_HTTP_PORT` (8788) is the agent edge. Move either in `.env` if something on your machine already holds it — but read §3.2 first, because moving `REST_PORT` moves the OAuth redirect this gateway sends to providers.

**Never publish 8787 on `0.0.0.0`.** Everything in [`../SECURITY.md`](../SECURITY.md) turns on that one line. The shipped compose file is safe; a hand-written `docker run -p 8787:8787` is not.

### Where your credentials live

Connector secrets — OAuth tokens, app passwords, access URLs — are sealed in an encrypted vault and referenced from the database by an opaque `secret_ref`. They are never stored in a data row and never echoed back by any route.

The vault's master key is autogenerated on first boot and persisted inside the `pci_master_key` volume (mounted at `/app/.pci`). **That volume is not optional and not disposable.** `docker compose down -v` removes it, and every stored credential becomes undecryptable — the gateway will then refuse to boot rather than start green and fail at the first sync. Take a backup before you touch volumes: [`runbooks/backup-restore.md`](runbooks/backup-restore.md), and the whole rationale is in [ADR 0033](specs/decisions/0033-vault-key-fail-closed-boot.md).

## 2. The shape of a connection

Three nouns, and the Console does all of it for you — but knowing them makes every error message legible.

- A **credential** is one consent: one Apple ID, one OAuth grant, one Plaid Item, one Home Assistant token. Its secret is sealed in the vault.
- A **connector** (a *connection*, in the Console) is one credential × one sector. One credential fans out to as many as it covers — an iCloud app-specific password produces three connections (mail, calendar, contacts) from a single paste.
- The **connection id** is the id every cached row carries. Each Plaid Item is its own credential, so **one bank is one connection**; there is no single "Plaid connector".

The six sectors are `finance`, `health`, `mail`, `contacts`, `calendar`, `home`. They are the unit of permission: a grant names sectors, and a granted sector covers reading *and* acting across every provider in it.

## 3. Connecting your sources

Open the Console and click **Add a source**. The sources fall into four classes with genuinely different effort.

### 3.1 Paste a credential — the easy class

Nothing to register, nothing to approve. You paste one secret and the connections appear.

**SimpleFIN (finance, free).** Sign up at SimpleFIN Bridge, connect your banks there, and it gives you a **setup token** — a long base64 string. Paste it into the Console. The gateway claims it exactly once, converts it to a durable **access URL**, and seals *that*; the setup token is single-use and is never the stored secret. If you already hold a claimed access URL (it looks like `https://…@bridge.simplefin.org/…`), paste that instead — it is detected and sealed directly.

> **Why SimpleFIN is the default and Plaid is the upgrade.** The US has no PSD2, so there is no free, universal, real-bank-data API for US accounts. SimpleFIN is a small paid-by-you bridge with wide coverage and one portable token. Plaid gives better coverage and richer enrichment but bills per linked bank. In the EU, Enable Banking is the free successor to GoCardless's free tier (closed to new signups in July 2025). Connect Plaid only for the banks SimpleFIN cannot reach.

**iCloud (mail + calendar + contacts).** In your Apple ID settings, create an **app-specific password** — never your real password, which will not work here and should not be pasted anywhere. Paste the Apple ID and the app-specific password. One credential, three connections, all read-only. The connector talks IMAP for mail, CalDAV for calendar and CardDAV for contacts; see [ADR 0030](specs/decisions/0030-icloud-dav-connector.md).

**Gmail (mail).** Create an **app password** on your Google account and paste it with your Gmail address. The App-passwords page **does not exist until 2-Step Verification is on** — no amount of searching the Security page will surface it before that. Turn 2SV on first, then go directly to `myaccount.google.com/apppasswords`. Google shows the 16 characters in four space-separated groups; paste it however you like — the whitespace is stripped before sealing.

> **Gmail is IMAP on purpose, and it stays IMAP.** Moving Gmail onto the Gmail API triggers Google's annual CASA security assessment for every deployment of this software, which is not a cost a self-hosted personal gateway can carry. The Google OAuth app below therefore requests **no** Gmail scope, ever — a test enforces it. See [ADR 0002](specs/decisions/0002-connector-auth-casa-free.md).

**Home Assistant (home).** Create a **long-lived access token** in your HA profile. Paste it along with your instance URL. Use a LAN address (`http://192.0.2.10:8123`) — an mDNS `.local` name does not resolve from inside a container. This is the one connector that also *acts*: its service catalog is served from the cache and dispatched through `invoke_action`, with the admin and system service domains denylisted from both the catalog and dispatch ([ADR 0003](specs/decisions/0003-ha-action-model.md)).

### 3.2 Bring your own OAuth app — Google, Microsoft, WHOOP

This gateway ships **no shared OAuth client**, and cannot: a confidential client secret embedded in open-source software is not a secret. So you register your own app with the provider once, paste its `client_id` (and secret, where the provider is confidential), and consent to your own app. Nothing about your data touches this project's infrastructure, because there isn't any. ([ADR 0014](specs/decisions/0014-oauth-byo-app-confidential.md).)

> ### The redirect-URI trap — read this before you register anything
>
> Every one of these providers **exact-matches** the `redirect_uri` string. One character off and consent fails with an error that blames a URI you never typed.
>
> **Do not compose the redirect URI by hand, and do not copy it out of this document.** Ask your own gateway what it will send:
>
> ```bash
> curl -s localhost:8787/api/oauth/google/app | grep -o '"redirectUri":"[^"]*"'
> ```
>
> That value is generated by the same function the consent flow calls, so it cannot drift from what is actually sent. The Console's connect screen renders the identical string for copying. Register *that*, verbatim.
>
> On a stock install it is `http://localhost:8787/api/oauth/<provider>/callback`. It **follows `REST_PORT`** — move the port and the registered URI must move with it. The host half is pinned to `localhost` and is never derived from the request, so a proxy or a `127.0.0.1` address bar cannot change it. It is also **never** a `*.ts.net` tailnet name: Google requires DNS-level ownership verification of a redirect's domain, Tailscale owns the `ts.net` zone, and `ts.net` is on the Public Suffix List — so that configuration is not discouraged, it is impossible ([ADR 0035](specs/decisions/0035-public-exposure-is-a-supported-path.md) §D5).

**Google** — Calendar and Contacts, read-only. Everything happens inside **one** Google Cloud project. First enable the two data APIs there: APIs & Services → Library → **"Google Calendar API"** → Enable, then **"People API"** → Enable — and mind the search results: contacts data comes through the **People API**; the similarly-named legacy "Contacts API" is deprecated, appears first when you search "contacts", and enabling it does nothing. Then configure the **OAuth consent screen** (the modern console names it **Google Auth Platform → Audience**) before anything else — the Clients page refuses to mint a client until one exists. Choose **External** (Internal is only offered to Google Workspace organizations), fill in the app name and contact emails, and — the step that blocks the whole flow if skipped — **add your own address under Test users**: while the app's status is Testing, Google refuses consent for any account not on that list, with *"OAuth access is restricted to the test users listed on your OAuth consent screen."* Then create an OAuth client of type **Web application** and add the redirect URI. Google is a **confidential** client here: paste both the client id and the client secret, or the token exchange fails. At sign-in, two screens deserve forewarning: the *"Google hasn't verified this app"* interstitial (**Continue** is the small link — the prominent button aborts), and the scopes screen, whose **checkboxes start empty** — tick "Select all" or the consent "succeeds" while granting nothing. If a sector then errors with a bare **403 right after a successful consent**, the API for it is not enabled in the client's project — enable it, give Google a minute, and Reconnect.

> **The 7-day re-consent, stated plainly.** A Google Cloud project left in **"Testing"** publishing status expires refresh tokens after **7 days** when sensitive scopes are involved — and Calendar and Contacts are sensitive scopes. Because every user brings their own app, every user meets this. You will re-consent weekly until you move your project's publishing status to **"In production"**, which for a single-user app you own is a form you fill in, not a review you wait on. This is a known cost of the BYO-app model and there is no code-side fix for it.

**Microsoft** — Mail, Calendar and Contacts. On a brand-new personal account, entra.microsoft.com walks you through creating a free Azure (or Microsoft developer) account before **App registrations** appears — budget five minutes and don't be alarmed. Register an app with supported account types **"Any Entra ID Tenant + Personal Microsoft accounts"** (the `signInAudience` covering personal and work accounts), and add the redirect URI under the **"Mobile and desktop applications"** platform — the registration form's dropdown calls the same thing **"Public client/native (mobile & desktop)"**. Microsoft is a **public** client: use PKCE and leave the secret unset. Unlike Google, there is **no API-enabling step and nothing to add under "API permissions"**: the gateway asks for the read scopes at sign-in, and the consent page — *read your mail, read your calendars, read your contacts, maintain access* — is where you grant them.

> **If Microsoft asks you to sign in every day, it is your app registration, not a bug.** A redirect URI registered under the **SPA** platform caps Entra refresh tokens at **24 hours**. The same URI under "Mobile and desktop applications" gets the 90-day rolling refresh. This was diagnosed the hard way; the token-refresh code was correct all along.

**WHOOP** — health. Register an app in the WHOOP developer dashboard with the redirect URI and the read scopes. WHOOP is **confidential-only** (no public client type exists) and it ignores PKCE, so the secret is the only proof — paste both. Its refresh additionally requires the `offline` scope, which the gateway requests for you.

Once the app is configured, click Connect. The gateway builds the authorization URL, you approve in your browser, and the callback creates one connection per sector the granted scopes actually cover. **The consent window is 10 minutes** — the pending PKCE state is held in memory with that TTL and is single-use, so if you wander off mid-consent, start again from the Console. A gateway restart mid-consent also loses it.

### 3.3 Plaid — your own app, then a hosted Link session

Plaid is its own class because it is per-bank and it bills. The full walkthrough is [`runbooks/plaid-onboarding.md`](runbooks/plaid-onboarding.md); the shape is:

1. Create a Plaid developer account and copy your `client_id` and your **Production** secret.
2. Paste them into the Console with the environment (`sandbox` or `production`). Only the exact string `production` leaves the sandbox, so a typo fails safe.
3. Click Connect. The gateway mints a Plaid-hosted Link URL, opens it, and **polls** for the result — there is no embedded widget, no token to paste, and no inbound webhook, which is what makes it work on a loopback-only box. One session can add several banks; each becomes its own credential and its own connection ([ADR 0019](specs/decisions/0019-plaid-hosted-link-onboarding.md)).

You do **not** register a redirect URI with Plaid for this flow. Connections you made previously at `my.plaid.com` do not transfer — Plaid only reads banks linked through this gateway's own Link session.

Bank consent expires roughly annually. The Console shows a per-connection health state and a Reconnect action; disconnecting calls Plaid's `/item/remove` so a removed bank stops billing ([ADR 0020](specs/decisions/0020-plaid-connection-health-and-relink.md)).

### 3.4 Apple Health — your phone pushes to you

Nothing can read Apple Health from off your phone, so this one inverts: the Console mints a per-connection ingest endpoint and a 256-bit secret, and your iPhone POSTs your metrics to it on whatever schedule you set. Postern keeps what your device chooses to send, from the day you start sending it; that is a faithful cache of a push, not a backup of your Health store.

The path that runs in production is the **Health Auto Export** app (App Store; its REST-API automations may need the app's paid tier). Two automations, split by data type, both: Destination **REST API** · URL = your ingest endpoint · header `Authorization: Bearer <your ingest secret>` · Format **JSON** · Export Version **v2** · file length **day** · Aggregate Data **on**, Aggregate Sleep **on**. Automation one exports **Health Metrics** (pick your metrics; cycle tracking and medications are toggles), automation two exports **Workouts** (metadata and routes on). Set the schedule, run one manually, and watch the first rows land in the Console. A hand-built Shortcut POSTing the same payload works too — the template is on the connect screen. One warning: an exported HAE automation JSON contains your live secret and ingest URL — scrub both before sharing one as a sample.

The ingest route is deliberately the one route with no loopback restriction — its per-connection hashed secret is its gate, verified in constant time and fail-closed ([ADR 0008](specs/decisions/0008-push-ingest.md)). To reach it from your phone when you are not at home, see §5.

## 4. After the first sync

**Mail is windowed.** Mail connections cache a **recency window**, 180 days by default, per connection and changeable from the Console. Older mail is not cached — it is reachable on demand by id through `fetch_live` / `get_record`. This is deliberate: an unbounded initial sync of a large mailbox is slow, multi-cycle and fragile, and an agent almost never needs deep archive for context. Growing the window backfills; shrinking it never prunes what is already cached ([ADR 0017](specs/decisions/0017-mail-recency-window.md)).

**Freshness is a derived word, not a timestamp you interpret.** Each connection reports `ok | syncing | stale | unreachable | error | paused | disconnected | never_synced`, computed server-side in exactly one place and served identically to the Console, `describe_context`, and the REST mirror. `unreachable` means a push stream is down and the cache is quietly aging even though the connection looks active ([ADR 0023](specs/decisions/0023-uniform-freshness-state.md)).

**Money is signed and negative means money out.** Every provider is normalized to that rule on write, including account balances — a liability owed is negative everywhere. It is the single most common source of wrong answers, which is why `get_schema` states it per field.

**Poll cadence is yours to set,** per connection, clamped to a floor each connector declares from its own provider's rate limits ([ADR 0025](specs/decisions/0025-sync-cadence-and-webhook-tiering.md)).

## 5. Reaching your gateway from away

The gateway binds loopback on purpose, and "remote access" never means "expose the gateway" — it means putting an authenticated front in front of the three surfaces that were designed for remote use (device ingest, the MCP edge, and the optional REST read mirror).

The blessed path is **Tailscale `serve`**: tailnet-private, end-to-end encrypted, no port forwarding, works behind CGNAT, and the HTTPS private key never leaves your machine. For the Console itself, an SSH tunnel is enough — `ssh -L 127.0.0.1:8787:127.0.0.1:8787 <host>`.

Hosted web clients (claude.ai, ChatGPT) connect from the vendor's own servers and can never reach a tailnet, so they need a genuinely public endpoint. That is **supported and first-class**, never a default and never a side effect: you opt in from the Console's Settings screen, and a gateway whose owner never opts in stays byte-identically loopback-only. Tailscale Funnel is the recommendation because TLS still terminates on *your* machine — a fronting CDN that decrypts at its edge would put your transactions, workouts and mail in plaintext on someone else's network.

Everything about this — the port-443-only constraint, what exactly is exposed, what to harden first, and how to verify it — is in [`runbooks/remote-access.md`](runbooks/remote-access.md). Read it before you publish anything.

## 6. Connecting an agent

### Mint a key

In the Console: **Agents → new**. Name the agent, tick the sectors it may reach, and set an expiry. The key is shown **once** and only its hash is stored — there is no way to recover it later, only to rotate it.

Grants are **default-deny** and **domain-level**: a granted sector covers both reading and acting across every provider in it, and there is no per-connector, per-action or per-call gating. An agent with no sectors connects successfully and is denied on every read; that is the intended shape, not a bug.

### Point a local client at it

Any harness running on your own machine or your own tailnet talks to the MCP edge over HTTP with the key as a bearer token:

```bash
claude mcp add --transport http postern http://127.0.0.1:8788/mcp --header "Authorization: Bearer <your-key>"
```

Cursor and other clients take the same URL and header in their own MCP config. Claude Desktop needs an stdio bridge (`mcp-remote`) in front of the same URL.

### Point a hosted client at it

claude.ai and ChatGPT will not accept a static bearer, so the gateway ships a minimal OAuth 2.1 authorization server on the MCP edge where **your pasted agent key is the login** ([ADR 0029](specs/decisions/0029-mcp-oauth-bridge.md)). It is **off** unless you publish an address, and byte-identical to the non-bridge behaviour when off.

Two things bite here, in this order:

- **Cloud MCP connectors egress on port 443 only.** A Funnel on any other port gets a silent TCP reset before a request leaves the vendor's network: the client says "couldn't reach", and your logs show *nothing at all*, because nothing arrived. This is an observed behaviour, not a published vendor contract — treat it as something that could change in either direction.
- **The published address is an origin, not a URL.** A bare `https://host` — never a path, never a port. A path-carrying value makes the bridge advertise discovery endpoints that 404 on the gateway itself, with every health signal green.
- **The connector URL is that origin plus `/mcp`.** The address you *save* in Postern is the bare origin; the address you *paste into claude.ai* is `https://<host>/mcp` — the Console's connect card shows the exact value to copy. If a connect fails, fix the URL, wait five minutes, and try once: claude.ai caches a failed check for a few minutes, so immediate retries only keep it looking broken.

Give any cloud-facing key an **expiry**. It lives on someone else's infrastructure, and an unexpiring key handed to a cloud service is a credential you can only ever end by noticing. Rotating or revoking the key kills every token derived from it, by design.

## 7. Optional configuration

Everything above works with the single `POSTGRES_PASSWORD` line you already wrote. For anything else, add lines to that same `.env` — `.env.example` documents every variable in place, with the trap attached, so copy the ones you need out of it rather than over the top of your password. The ones people actually reach for:

| variable | why |
|---|---|
| `POSTGRES_PASSWORD` | required; no default |
| `REST_PORT` / `MCP_HTTP_PORT` | something else holds 8787 / 8788 — and see the redirect-URI trap |
| `PCI_MASTER_KEY` | you want to hold the vault key yourself instead of letting it autogenerate. Base64 of exactly 32 bytes, and it must be set **before** first boot |
| `REST_ALLOWED_HOSTS` | you reach the Console through a hostname the gateway would otherwise reject. This widens what is *accepted*; it adds no identity check |
| `MCP_PUBLIC_URL` | the headless equivalent of publishing from the Console |
| `HA_URL` | headless Home Assistant address; the per-connection field in the Console is the better path |

Console-configured provider credentials are stored in the database with their secrets sealed, and they **win** over the environment. The `*_OAUTH_CLIENT_ID` / `PLAID_*` variables exist as a headless fallback for deployments that never open a UI.

## When something is wrong

- **The Console 404s but `/healthz` is fine.** The built Console assets are not where the server looked. It says so once on stderr with the path it tried; `PCI_CONSOLE_DIR` overrides it.
- **Consent fails with a redirect mismatch.** The registered URI is not byte-identical to what the gateway sends. Re-read it from `GET /api/oauth/:provider/app` and compare character by character — scheme, host, port, path, no trailing slash.
- **"Provider not configured" (400) on connect.** No client id is resolvable — neither a Console-saved app nor the environment fallback.
- **A source shows `unreachable` while everything looks connected.** A push stream is down and retrying; the cache is aging. That word exists precisely so this stops being invisible.
- **The gateway refuses to boot after a restore or a volume change.** The vault key cannot open the sealed rows. The message names the key id and the first failing reference. Check `PCI_MASTER_KEY_ID` first — a diverged *label* is the most common cause, and the key itself is usually fine.
- **You want to see everything the gateway holds.** `GET /api/export` returns the whole store, unscoped, from loopback. Erase is a real hard delete and it is not reversible ([ADR 0012](specs/decisions/0012-data-control-plane.md)).
