00  Design principles

The invariants.

Non-negotiable in V1. A change that violates one is wrong by definition, not by taste.

North star — the three mantras

Every principle below serves these, and every design decision is measured against them — if a choice weakens one, it's the wrong choice. One place: your whole life behind one surface and one grant, not N apps with N configs. Lightning fast: reads serve from the local cache in ms; actions add zero gateway overhead around the single unavoidable dispatch — we never long-poll the source on the hot path. Harness-agnostic: swap the harness, keep the context, the capabilities, the permission, and the audit — paste a URL into any agent.

  1. We are the gateway, not the brain. The agent reasons; we authenticate, normalize, store, and serve. No LLM on our side — the agent composes queries, we execute them deterministically.
  2. The context is the product; the agent is a replaceable client. Everything is built so a user can swap Claude → a local model → whatever's next without losing context. Neutrality and portability are load-bearing.
  3. Everything is a connector — and eventually connectors author themselves. A new source is only a new adapter that maps into the normalized schema (no per-source logic above the connector layer). The V0 core is hand-built; the SDK extracted from it then lets an agent author the long tail — sandboxed, gated by a conformance harness. Breadth writes itself, once the contract is proven.
  4. Borrow at the connector; own the normalized store. You may wrap existing OSS to ingest a source, but the normalized rows and the query surface are always ours and uniform.
  5. Adopt standards, not apps. Each domain's schema is derived from its open standard (vCard, iCalendar, OFX/Plaid model, FHIR/HealthKit) — never from one application's database.
  6. One store, one uniform surface. Per-domain normalized tables in one database, behind one query API. Not a federation of heterogeneous app databases.
  7. No cross-domain correlation in V1. No entity resolution, no derived facts, no joins across sectors. The agent correlates at query time. (That layer is the moat — chapters 2/3.)
  8. Lossless gateway: reads AND actions, no regression. We are a gateway, not just a store — if a source already lets an agent act (Home Assistant toggling a light with its token), routing through us must not strip that. So we expose whatever the connected credential supports — reads and actions — and add portability, one surface, and an audit trail on top. Two kinds of "write", kept distinct: actions (commands sent OUT to the source — toggle a light, send mail) are in V1; derived-store writes (annotations / agent-authored values, e.g. your own category) stay the planned chapter-2 first feature. Actions dispatch to the provider then trigger a targeted re-sync; they never fabricate data in the store, so it stays a faithful cache — bounded by the credential's own scopes, never exceeding the source grant.
  9. User-owned by construction. Connect once; see / export / delete everything; every agent is default-deny, scoped per sector, revocable, and audited.
  10. Design the seams, build the simple impl. SecretStore, Auth, and tenancy are interfaces. V1 ships the self-host implementations; hosted swaps in cloud KMS / multi-tenancy / OAuth without a rewrite.

02  Components

Each layer, and what it must not do.

Connectors — the one unit of extension

A small adapter for a single source. It authenticates, pulls raw records, normalizes them into the domain's schema, declares deterministic strong keys (recorded now, used later by chapter-3 resolution), and — where the source supports it — declares an action catalog (ActionSpec[]) and executes those actions. Reads fill normalized rows; actions dispatch OUT to the source, then a targeted re-sync reflects the result. Read-only connectors declare an empty catalog. Connectors never correlate, derive, or interpret.

export interface Connector<TNormalized = unknown> {
  readonly provider: string;     // "simplefin" | "plaid" | "gmail" | ...
  readonly sector: string;       // "finance" | "health" | "mail" | ...
  readonly objectType: string;   // "transaction" | "message" | ...
  readonly actions: ActionSpec[]; // declared action catalog — [] for read-only

  sync(ctx: SyncContext): AsyncIterable<RawRecord>;   // pull since cursor
  normalize(raw: RawRecord): TNormalized;             // → the domain schema
  strongKeys(raw: RawRecord): Record<string, string>; // deterministic keys
  execute(id, params, ctx): Promise<ActionResult>;    // dispatch a declared action OUT
}

This interface and the normalized schemas are the public contract of the project — they live in the permissively-licensed @pci/sdk package so anyone can build and publish connectors. Two providers per sector (SimpleFIN and Plaid; Gmail and Outlook) is the forcing function that proves a schema is genuinely provider-neutral. The V0 core is hand-built (agent-assisted); the contract extracted from it then lets an agent author the long tail — run in a sandbox (scoped token, egress-limited) and admitted only on passing a conformance harness. See Agent-Authored Connectors.

Normalized store

One Postgres database. Each sector has its own table-set; there are no foreign keys or joins across sectors. Every domain table is the same template — id uuid PK (the get_record drill key) / connection_id → connectors / user_id / source_object_id (the provider id) / normalized columns / raw jsonb / ingested_at / unique(connection_id, source_object_id) — so the surrogate uuid PK (never the provider id) keeps it multi-user and multi-connection safe and the upsert idempotent. get_record drills to source truth via the raw payload. A small in-code registry (src/core/schema.ts) declares, per sector, the table and its queryable fields, and the query API validates every field against it. Full table-by-table definitions: Data Model.

Not here in V1

No source_events / entity resolution / derived_facts. Those belong to chapters 2–3. V1 is normalized per-domain rows and nothing more.

Core API — the seven primitives

Plain functions over Postgres. Everything else (MCP, REST, CLI) is a thin adapter over it — never a second implementation. "Anything and everything" comes from a few powerful primitives, not a tool per question: the agent introspects the schema, composes any query, drills to raw, forces a live fetch, or discovers and invokes an action — without us anticipating questions. Cross-sector breadth is a fan-out, not a join.

Freshness & speed — the gateway is the cache

There is no separate cache tier. The pipeline is sync → local store → serve: connectors pull each source into Postgres on their own cadence, and reads are served from that store. So query and get_record are always cache-only and instant — they never touch a provider. fetch_live is the one upstream path (opt-in, bounded), and describe_context exposes each connector's last_synced_at so the agent self-serves the freshness/latency tradeoff rather than us guessing it. No Redis or second cache tier in V0 — indexed, capped, projected Postgres is the cache; the only in-memory caching worth doing is get_schema / describe_context.

Freshness is connector-declared policy, not code. Each connector ships a SyncPolicy and a generic scheduler orchestrates all sources identically — there is no bespoke per-sector sync path:

modescheduler behaviore.g.
pushregister the source's subscription/webhook; update the store on each eventHome Assistant
pollrun sync() on a cadence, pulling deltas from the cursorSimpleFIN, Whoop
on_demandnever auto-syncs; only fetch_live touches it—

Every domain table is one template, so indexing is generic too: each registry object declares a primaryTime, which drives both the (user_id, connection_id, primaryTime) hot-read index and the default sort. And because the store is the source of truth for reads, query supports server-side aggregation (sum / count / avg) — the agent never ships rows home to reduce them.

Actions are cache-first too — the slow part of acting is discovery, not the dispatch. Acting naïvely means a chain of live polls (enumerate entities → filter → check state → check supported services), then one command. We serve that discovery from the cache + the static action catalog (ms, same as reads), so only the single dispatch is live. Three moves keep an action ~one-shot, with no extra gateway round-trips:

  • Typed MCP tool at connect — the tool list is the catalog. Each connector's ActionSpec[] is exposed as a typed MCP tool when the connector is wired, so there's no list_actions round-trip on the hot path; the generic invoke_action stays for REST/CLI peers.
  • Deterministic target resolution, server-side. invoke_action accepts a structured selector (area / domain / name) resolved against the cache server-side with no LLM on our side, so "the kitchen light" is one call, not query-then-act.
  • Non-blocking reconciliation. The action returns immediately; the push stream (or an optimistic write) updates cached state afterward — no synchronous re-poll on the response, consistent with the async-audit, never-blocking model.

The honest floor: the one live dispatch is bounded by the source — everything around it is instant. (Permission stays domain-level: a granted sector covers read AND act; nothing here adds a per-action gate.)

Adapters

  • MCP server (primary). Remote (Streamable HTTP) for "any agent, one URL"; stdio for local single-agent use. Tools map 1:1 onto the core primitives. (Transport, sessions & the keep-alive reality: §05.)
  • REST API (the core surface). What the Console UI consumes and the protocol-risk hedge — if MCP is superseded, swap the adapter; the core stands.
  • CLI (secondary). Terminal/coding harnesses, scripting, tests.

Console UI & control plane

The Console is the connect / permission / export / audit surface and the consent front door — not a dashboard, not an assistant. It talks to the REST API (a prerequisite for the UI) and is bundled in Docker Compose. Behind it sits a six-table control plane — one chain from a user to an audited read (full schema in Data Model):

tablewhat one row is
usersthe tenancy anchor; one seeded row in self-host, more rows (no migration) when multi-tenant
secretsthe vault — a token encrypted at rest; everything else references it by secret_ref, never the blob
provider_credentialsone authenticated consent (one Google OAuth, one SimpleFIN access URL); carries the custody mode and points at secrets
connectorsone credential × one sector. connectors.id is the connection_id FK on every domain row; runtime sync state (cursor, last_synced_at) lives here
agent_grantsper-agent, default-deny sector scopes (empty = nothing), revocable; the API-key hash lives here, never the raw key
audit_logappend-only, one row per core call — allow and deny; the app role has UPDATE/DELETE revoked

The credential / connector split is load-bearing: one consent fans out to many sectors. A single Google credential yields three connectors — mail, contacts, calendar — so the user consents once and the gateway treats each sector as an independent, separately-permissioned connection. Adding a sector is a new domain table plus a registry entry; it is never a control-plane change.

The authoring substrate — the breadth flywheel

After the V0 core is hand-built, breadth comes from an owned substrate — and that substrate is the moat: the SDK + schema contract (the target an agent writes against), a sandboxed runtime (generated code runs with no ambient secrets — only the scoped token, egress restricted to the source's domain, with CPU/time/memory caps), and a conformance harness (validates schema-valid rows, idempotency, pagination, and auth refresh before a connector is trusted). The connectors are generated (commodity) and the SDK is open (Apache); the sandbox + harness are what we own — trustworthy generation is the product. Full design: Agent-Authored Connectors.

On reusing app databases

SureFin and similar OSS finance apps are design references only — we build our own SimpleFIN/Plaid connectors mapping into our schema, to avoid a dependency and keep the surface uniform. Borrow at the connector if it saves real ingestion work; never adopt an app's database as ours.

05  Security & auth

Self-host first deletes the two hardest pieces.

V1 is self-host first, single-tenant: the operator owns the box and the disk. Two auth questions stay strictly separate — how an agent reaches the gateway, and how the gateway reaches a provider.

Agent → gateway — three tiers

tiermechanismwhen
localstdio MCP, no auththe operator's own agent on the same box
remoteper-agent scoped bearer API keys — generated in the Console, scoped to sectors (default-deny), audited; only the key hash is stored in agent_grantsmultiple / remote agents
OAuth 2.1 AS(deferred) — a full OAuth authorization serverthe hosted / multi-tenant chapter

There is no OAuth authorization server to run in V1. Scoped bearer keys are the entire agent-auth surface; the AS is a hosted-chapter concern, behind the Auth seam (principle 10).

How agents connect — transport & the keep-alive reality

MCP is the surface, and the connection model differs by transport — "a keep-alive connection" only half-describes it. Local (stdio) genuinely is persistent: the harness spawns the gateway as a subprocess and holds one stdin/stdout pipe open for the whole session, reused across every tool call — no network, no handshake. Remote (Streamable HTTP) is not a custom long-lived socket: each JSON-RPC message is an HTTP POST to one endpoint, answered with either a plain JSON response or an optional Server-Sent-Events stream; session continuity rides the Mcp-Session-Id header (it outlives any single TCP connection), and "keep-alive" is just ordinary HTTP connection reuse. Use the SDK's StreamableHTTPServerTransport — never hand-roll a socket.

Where latency actually goes. Reads are milliseconds from the local store (§02), so the gateway's own work is rarely the bottleneck — transport setup is. Locally the persistent pipe already eliminates it. Remotely, opening a fresh TCP+TLS connection per call (~1 RTT each) would dwarf a sub-millisecond read; ordinary HTTP keep-alive / connection pooling fixes it by reusing one warm connection across calls. The win is at the HTTP layer, not a bespoke MCP channel.

A non-MCP harness still connects. If it speaks MCP, wiring it up is config-only (add the stdio command, or paste a URL + key). If it has tool/function-calling but not MCP, point ~5 thin wrappers at the REST mirror — or use an MCP→function-calling adapter, which imports the tools and keeps get_schema discovery for free. If it can only shell out, wrap the CLI. MCP support is a convenience, not a requirement; the only harness that can't connect is one with no tools, no HTTP, and no shell.

The static-bearer deviation

The MCP authorization spec expects HTTP transports to be OAuth 2.1 resource servers. V1's scoped static bearer is a deliberate, wire-compatible deviation until the hosted OAuth AS lands — so a strict MCP client that demands the OAuth discovery handshake may reject a plain bearer. The reliable V1 paths are therefore stdio locally and bearer-tolerant clients remotely, with manual key entry as the fallback.

Gateway → provider — the custody enum

Provider-side OAuth (the gateway acting as a client to Google / Microsoft / Whoop) is a different axis, modeled on provider_credentials.custody: static_token (SimpleFIN access URL, Home Assistant long-lived token — no OAuth app), byo_app (the operator brings their own OAuth client), hosted_broker (a broker we run hands out client credentials), on_device (reserved). This is what lets one box reach an OAuth source without standing up an authorization server of our own.

Encryption

Per-user envelope encryption (DEK/KEK) is a multi-tenant honeypot concern. Single-tenant self-host: the operator owns the box and the disk. So V1 encrypts connector secrets at rest with a local master key (SecretStore), relies on the operator's disk encryption for the rest, and defers per-user DEKs to the hosted chapter — behind the same seam.

The self-host wrinkle: OAuth client credentials

A self-hosted box reaching Gmail/Outlook/Whoop needs OAuth app credentials. Two supported custody modes cover it: byo_app — the operator brings their own app (privacy-pure, some setup) — or hosted_broker, a broker we run. static_token sources (SimpleFIN, Home Assistant) avoid this entirely, which is why they're the first connectors.

Threat model (V1)

Trusted: the operator and their box. Defended: agent over-reach (default-deny + scope + audit), secret theft from a data dump (secrets encrypted, referenced by secret_ref), over-reaching actions (bounded by the credential's own scopes — we never exceed the source grant — plus the domain grant + async audit). Out of scope for V1: a compromised host OS, and multi-tenant isolation (there is one tenant).

07  Licensing

Permissive throughout.

  • Everything: Apache-2.0 — SDK, connectors, server, Console. An AGPL SDK cannot be linked by a commercial connector or agent author without opening their own source, which forecloses the third-party ecosystem the platform exists to have.
  • The moat is not the licence. It is the broker position with the identity providers, the registry, and the trademark — none of which a copyleft clause protects, and all of which survive a fork.
  • Contributions: DCO sign-off, inbound under the same terms. No CLA: Apache is the terminal choice here, and keeping later components proprietary needs no relicensing of what already shipped.
08  Roadmap — the three-chapter ladder

Same ambition, sane sequence.

Each chapter is additive over the one before, reads from the substrate you already own, and is gated on signal, not a calendar.

chapterwhat you addrent / buildclimb when
1 · Gatewaythis — neutral, no-correlation access to the sectorsbuildnow
2 · Recallsemantic + temporal search and cross-session memory — a recall() tool beside query()rentusers want "search across everything"
3 · Canonicalcross-source resolution, derived facts, corrections that win forever (the moat)buildbreadth has proven out and someone is matching it
Where a rented engine fits — and where it does not

A memory engine (Mem0 / Graphiti / HydraDB) is legitimate for recall (chapter 2): a rebuildable index over our normalized store, behind an adapter, chosen by a bake-off on real data. It must never own chapter 3 — identity and truth. Those engines decide merges with an LLM, which cannot hold a deterministic precision bar or honor corrections forever, and would make the user's context portable to the vendor, not the user. Recall is rentable; identity-and-truth is the IP.

10  Glossary

Terms.

  • Sector — a domain of life (finance, health, mail, contacts, calendar, home).
  • Connector — an adapter for one source that normalizes into a sector's schema.
  • Normalized store — per-sector tables; the only place data lives; no cross-sector joins.
  • Core API — the seven primitives (five reads + list_actions / invoke_action); the single place permission/cost/schema/audit are enforced.
  • Adapter — MCP / REST / CLI surface over the core (no logic of its own).
  • Console — the connect/permission/export/audit UI.
  • Recall (ch. 2) — rented semantic/temporal search over the store.
  • Canonical (ch. 3) — the owned resolution + correction layer (the moat).

Borrow at the edges. Own the core. Swap the harness, keep the context.
