The mental model

A uniform query-and-command layer over everything you’ve connected — with a cache for speed and a live path for truth.

A Volvo, a bank, Hue bulbs, a Whoop strap, your inbox — wildly different real-world APIs. Through the gateway an agent never learns those four (or forty) API shapes. It learns one: pick a sector, describe the fields, optionally act. Every source collapses to the same small surface.

The hard, slow part of working with a raw vendor API is discovery — enumerate the entities, filter them, check their state, check what’s supported. The gateway pre-pays that discovery tax once, during sync, and folds it into an indexed local store. The agent re-pays it on every cold question against a raw API; through the gateway, it’s already paid. That single shift — moving cost off access and onto judgment — is the whole design.

The throughline

The agent supplies intent it discovered from us; the gateway owns all source I/O — auth, transport, pagination, rate limits, selector resolution, dispatch, the re-sync. Swap a Volvo for a Tesla, or Hue for LIFX, and nothing the agent knows changes: the discovery surface re-describes the new capabilities in the same shape.

The three mantras

Every design decision is measured against these.

01

One place

Your whole life behind one surface and one grant — not N apps with N configs. A new sector is a new table, never a new account.

02

Lightning fast

Reads serve from the local cache in milliseconds. Actions add zero gateway overhead around the single unavoidable dispatch. We never long-poll the source on the hot path.

03

Harness-agnostic

Swap the harness, keep the context, the capabilities, the permission, and the audit. Paste a URL into any agent.

The interface

Seven primitives — discover, read, act.

Everything an agent can do maps onto these seven functions. They are the MCP tools, and they are mirrored 1:1 by a REST surface (for non-MCP harnesses and the Console). Reads and writes are symmetric: each has a discover verb and a do verb.

PrimitiveKindWhat it does
describe_contextdiscoverWhich sectors you’re granted + each connection’s last_synced_at freshness. The agent self-serves the speed/freshness tradeoff from here.
get_schemadiscoverThe queryable fields + types for a sector (the read contract). Cached in memory.
queryreadStructured read from the cache — filters, operators, server-side aggregation. Always instant, never touches a provider.
get_recordreadOne record by id, drilled truthfully from the cache (tombstones included).
fetch_livereadThe one read-time upstream path (opt-in, bounded): a sector sync-now, or a per-record live drill against the source.
list_actionsdiscoverThe action catalog across granted sectors — served from the cache, never a live poll.
invoke_actionactPerform one action. We resolve the target deterministically and dispatch the single live call.

The symmetry that makes it learnable

get_schema + query are to reading what list_actions + invoke_action are to acting. Discover the surface from us (from cache), then do the one thing. The agent never crafts a vendor request and never holds a vendor credential.

A worked example

“When was the home last vacuumed?” — the canonical loop.

The rhythm is always the same: a broad cache query to find the right handle, then a narrow live fetch to trust the value.

solid = cache hot path (always instant)  ·  dashed = the one opt-in upstream path

  1. query { domain: "vacuum" } → finds two robots. The agent didn’t know their names; the cache let it discover them.
  2. fetch_live on the entity → it only carried state: docked, no clean-time. A cheap dead end.
  3. query { contains: "q5" } → surfaces 34 related entities, including the last_clean_end sensor. Fuzzy cache search is the workhorse for navigating without documentation.
  4. fetch_live on that sensor → confirms the cached value is still current.

Broad query to find the handle, narrow live fetch to trust the value. The same shape answers “how much did I spend on food in May?” (one sum aggregate over the cache) and “turn off the kitchen lights” (one invoke_action with an area selector).

The speed & freshness model

Cache-first, live-on-demand — and the system makes you choose.

Connectors sync each source into local Postgres on a cadence; agents read that store, never the provider API on the hot path. The gateway is the cache — there is no Redis, no second tier. Postgres, indexed and projected, is fast enough.

1 · Cache-first

query and get_record are always cache-only and instant. They support filters, the operators eq / neq / gt / gte / lt / lte / in / contains, and server-side aggregation (count / sum / avg / min / max with optional groupBy) — so “spend in May” is one summed number, not a thousand rows pulled to the agent.

2 · Live on demand

Cache can be stale. fetch_live is the explicit escape hatch when freshness matters. describe_context exposes each sector’s last_synced_at, so the agent decides — per question — whether “fast” or “true” wins. The tradeoff is surfaced, never hidden.

Freshness is connector-declared policy, not code. Each connector picks a SyncPolicy.mode — push (subscribe; e.g. Home Assistant streams over a WebSocket), poll (a cadence; e.g. SimpleFIN, Whoop), or on_demand — and one generic scheduler honors all three. Every sync mode stamps last_synced_at, so the freshness signal is honest whether the data arrived by poll, push, or webhook.

Footprint — bounded vs. unbounded

Bounded sources (finance, home, calendar, contacts, health) cache every row in full. Unbounded sources (mail, later Drive/Notion) cache only the envelope — sender, subject, snippet, dates, labels — so query stays instant and bounded; the body + attachments are fetched on demand via fetch_live, never stored. The connector picks its footprint; the sync engine is identical either way.

The live path

How fetch_live works — one verb, two modes.

The agent never talks to a provider directly — it has no vendor credential and no vendor endpoint, only our seven tools. So we fetch and hand back. What to fetch the agent learned from the cache (a record’s id, or a sector’s staleness); the fetch itself is ours.

mode: record

Per-record live drill

fetch_live({ id }). We resolve that cached row back to its own originating connection, call that source live, and return the raw provider payload — the source’s native shape, not our flattened columns. If the source says the object is gone, record is null and the cached row is tombstoned to match.

mode: sync

Sector sync-now

fetch_live with no id. We fan a refresh out to every active connection in the sector and wait up to 30 s, skipping push-mode connections (already live). timed_out: true means we stopped waiting — not that the sync was cancelled; it continues in the background, so the agent re-checks last_synced_at.

The two modes return different shapes on purpose. A drill returns the source’s native blob (that’s why a TV entity comes back with app_id, supported_features, an entity_picture proxy token — Home Assistant’s own attributes, not our row); a sync-now returns { synced, timed_out, last_synced_at }. Typed errors keep it honest: an absent connection or unknown id is a NotFoundError (REST 404); a source that can’t serve right now (e.g. the HA socket is down) is a FetchLiveUnavailableError (REST 502). Live fetches for footprint-limited sectors are never stored.

// the per-record drill: cache finds the id → we call the source → raw payload back
type FetchLiveResult =
  | { sector; mode: "sync";   synced; timed_out; last_synced_at; errors? }
  | { sector; mode: "record"; id; record }  // record: raw payload | null = gone

Acting on the world

The action path — the agent chooses what; we do every byte of how.

The agent does not know the catalog ahead of time, and we do not pick the action for it. It’s the read pattern, mirrored: list_actions to discover, invoke_action to do.

  1. list_actions — we serve the catalog from the cache, never a live poll. For a simple connector it’s a static list; for Home Assistant it’s the dynamic entity×service join (every controllable entity × the services it supports, with admin/system services denylisted). Each ActionSpec carries the action id (sector-namespaced, e.g. home.light.turn_off), its params, and the target it needs.
  2. invoke_action(id, params) — the agent hands us the chosen id + a target; we do the rest deterministically: grant-check the sector → resolve the active connection + its token → the connector resolves the selector ({ area: "Kitchen" } → the concrete light.* set, against the cache, server-side, no LLM) → fire the single live dispatch → async targeted re-sync + async audit.

So “the kitchen light” is one call, not query-then-act, and one call turning off eight bulbs is us fanning out a cached area membership — not the agent enumerating entities. Two ways to target: an explicit entity_id the agent got from a query, or a structured { area / domain / name } selector we expand.

The single dispatch has no retry — on purpose

The connector fires exactly one call_service and does not retry. For a real-world actuator (starting a car), blind auto-retry is dangerous, so an ambiguous downstream result surfaces as { ok: false } rather than being hammered. The action returns immediately; the push stream (or an optimistic write) reconciles cached state off the hot path. The honest floor: that one dispatch is bounded by the source’s own latency; everything around it is instant.

Under the hood

Inside the engine — the layers a call passes through.

Layer 0 · Transport & session. Locally, MCP runs over stdio — a persistent pipe, no auth, operating as the seeded local user. Remotely, it’s MCP over Streamable HTTP: a stateful session (the Mcp-Session-Id handshake) and a per-agent scoped bearer key (only its SHA-256 is stored). A “Missing or invalid Mcp-Session-Id” is a transport-layer error one level below any gateway logic — the fix is re-running the handshake, not retrying the call.

Layer 1 · The grant check is free. An AuthContext — { userId, agentId, grantedSectors } — is resolved once per session into an in-memory Set. Every call does assertSector → grantedSectors.has(sector): an O(1) membership check that throws AccessDenied before a single byte of SQL runs. No DB round-trip, ever. Default-deny: an empty grant set means the agent connects but every call denies.

Layer 2 · query compiles to parameterized SQL. Per call: resolve sector → table → validate every where/select/orderBy field against the published REGISTRY → map operators through a hardcoded whitelist (the agent’s operator string is never interpolated) → bind every value as a parameter. Two clauses are appended to every statement, non-negotiable: user_id = $n (you can never reach another user’s rows) and deleted_at is null (tombstoned rows never serve). It sorts by the object’s declared primaryTime desc, id asc — which maps exactly onto the generic (user_id, connection_id, primaryTime) index, so a default query is an index scan, projected, capped. It never accidentally sorts a full table.

A detail that signals the discipline

Monetary aggregates (sum/avg) return a Postgres numeric as a string, not a JSON number — serializing money through a float would round it. count returns a real number. Two return types from one tool, deliberately, to keep decimals exact.

Layer 3 · The write path does more. invoke_action resolves the target (selector → concrete entities, cached, server-side), validates against the action’s spec, checks the domain grant, dispatches once, and logs asynchronously. Audit is the only oversight: every read and action is logged off the response hot path (fire-and-forget) with the redacted args (a central key-denylist scrub) — detective, never preventive. It never blocks and never adds latency.

Where the vendor knowledge lives

The connector contract — one file per source, behind one interface.

This is the answer to “for each connection type, do we know exactly how to act and live-fetch via its API/SDK?” — yes, and it’s quarantined in one place. Every source-specific “how” — auth, the protocol, the dispatch — lives in a single Connector implementation and nowhere else. The seven primitives, the edges, grants, audit, the query engine are 100% source-agnostic and call this uniform interface.

interface Connector {
  readonly provider, sector, objectType;
  readonly policy:  SyncPolicy;        // push | poll(cadence) | on_demand
  readonly actions: ActionSpec[];        // [] = read-only
  listActions?(ctx, filter):  ActionSpec[];   // optional DYNAMIC catalog (HA)
  sync(ctx):                  AsyncIterable<RawRecord>;  // pull the data
  fetchRecordLive?(ctx, id):  unknown;        // the live drill (optional)
  decodePush?(rawBody):       RawRecord[];     // webhook decoder (optional)
  normalize(raw):             TNormalized;     // vendor shape → our columns
  strongKeys(raw):            Record<string,string>;     // dedup identity
  execute(actionId, params, ctx): ActionResult;  // perform the action
}

A new source is: implement this once + add a REGISTRY entry, and all seven tools light up. Four precisions worth holding:

  • “API/SDK” is whatever the source speaks, behind one wrapper. Home Assistant is a hand-built WebSocket client; SimpleFIN, Plaid, Google, Microsoft, Whoop are REST over HTTP (+ OAuth); Gmail is IMAP. All collapse to the same shape.
  • Only sources that can act declare actions. Today Home Assistant is the only actor (its catalog is the dynamic listActions join). The rest — finance, mail, calendar, contacts, health — are read-only: actions: [] and execute() throws. “We know how to act” is true per source, only where the source supports it.
  • The live drill and the push decoder are optional. A source implements fetchRecordLive only if it has one (HA live state; mail body-on-demand); a push source implements decodePush; a bounded poll source skips both.
  • Capability is bounded by the credential’s own scopes — we never exceed the source grant. Connectors are hand-built in V0, but against a frozen contract + a conformance harness that every connector (and future agent-authored ones) must pass.

In one sentence

For each connection type we encapsulate exactly how to sync, normalize, and — where the source + credential allow — act and live-fetch, behind one uniform interface. The agent sees none of it; it sees the catalog and schema we project from it.

The honest floor

The one live dispatch in an action, and any fetch_live, are bounded by the source — we can’t beat the device’s own latency. Everything wrapped around them is local-Postgres-and-RAM fast. That’s the bet, stated plainly.

The advantage

A gateway agent vs. a raw-API agent — same model, same questions.

A raw agent re-pays a discovery tax on every cold question — enumerate, filter, check state, check capability — that the gateway pre-paid once. Same answers, fewer round-trips, fewer tokens. Read that as the floor: zero-intelligence normalize-and-serve already wins. The memory/context layer (chapter 2) is the moat on top.

What the gateway carries vs. what the agent still does

The gateway eliminates the plumbing — auth, transport, pagination, rate limits, schema discovery (the tedious 80%). It does not do the judgment: classifying an uncategorized transaction by merchant, reasoning about which of two timestamps to trust, deciding whether the data actually answers the question. The friction moves off access and onto the genuinely interesting part.

The boundaries

What it deliberately is not.

No LLM on our side

The agent composes queries and actions; we validate and execute deterministically. Selector resolution, grant checks, SQL — all mechanical. The intelligence lives in the agent, never in the gateway.

A faithful cache, not a derived store

We authenticate, normalize, store, serve, and dispatch. We never write derived data into the store (that’s the chapter-2 memory layer). Actions go out to the source, then a targeted re-sync reflects the result — we never fabricate data.

No cross-domain correlation

Data is partitioned by sector with no joins between domains. To correlate spending with home activity, an agent fans out two queries and stitches them itself. The boundary is deliberate.

Not the account-linking UX

The gateway consumes established credentials — you link accounts at the source (a bank in SimpleFIN, a token in Home Assistant, an OAuth consent) and hand us the result. We add portability, one surface, and an audit trail on top; we never strip a capability the credential already had.

Using it

Point an agent at it.

Two paths, same seven tools, same domain grant:

  • Local (stdio) — the harness spawns the gateway over a stdin/stdout pipe; no auth, operating as the seeded local user. The reliable default for a local agent.
  • Remote (HTTP + bearer) — enable the MCP edge (MCP_HTTP_PORT, default 8788) and point any harness at http://localhost:8788/mcp with a minted bearer key in the Authorization header. Mint the key + choose its sectors in the Console.
// an MCP client config pointing at the remote edge
{
  "mcpServers": {
    "pci-gateway": {
      "type": "http",
      "url":  "http://localhost:8788/mcp",
      "headers": { "Authorization": "Bearer <your-minted-key>" }
    }
  }
}

The grant the agent gets is domain-level: a granted sector covers read and act across every provider in that domain. One scope, resolved once, checked in nanoseconds per call. Swap the harness and the context, capabilities, permission, and audit all come along — that’s the third mantra in practice.
