# ADR 0033 — The vault master key: compose-delivered, and a fail-closed boot scoped to keys that can actually break a sync

**Status:** Accepted · **Related:** #97 (items 1, 2, 3-backend), #105 item 1 (retire superseded vault blobs — still open), ADR 0011 (backup/restore + key rotation), ADR 0009 (packaging & runtime), ADR 0015 (the test-DB guard, and what a bypass costs)

## Context

One AES-256 master key seals every credential in the product. `secrets` (`db/schema.sql:47-56`) holds `ciphertext`, `nonce`, `aad` and a `key_id` naming which key sealed the row; `provider_credentials` holds only opaque `sec_<uuid>` refs. Lose the key and every stored credential is permanently unopenable. Two things about that key were broken, and one of them had been broken silently since the Docker packaging shipped.

**`PCI_MASTER_KEY` never reached the container.** The knob is fully honoured in code — `src/secrets/key.ts` asserts 32 bytes and fails closed with `MasterKeyError` — and it is the documented host-separation story in `docs/runbooks/backup-restore.md:66-67` and `docs/runbooks/key-rotation.md:73-74`. But nothing in the gateway reads a `.env` file (`grep -c dotenv package.json package-lock.json` → `0` / `0`) and `docker-compose.yml` had no passthrough line, so **every Docker user who set it silently landed on an autogenerated key anyway**. The documented escape from "your key lives in a Docker volume you can delete with one flag" did not exist.

**A wrong key surfaced weeks late, as a sync error.** Restore the database without its key, or let `docker compose down -v` regenerate a fresh one, and the gateway boots green, serves a healthy Console, and only fails at the first sync of each connection with a `SecretAuthError`. A recorded incident on a real deployment is the shape: a host-side `./.pci/master.key` that is *not* the key inside the container volume, producing a backup tarball that fails at restore with nothing but a silent auth error to go on. The failure is maximally distant from its cause.

**And the key notice was a one-shot line.** `src/secrets/key.ts` wrote a single stderr line at the moment of key generation. On a container that nobody watches boot, that is a warning nobody has ever read, guarding an unbounded and unrecoverable data-loss risk.

## Decision

### D1 · `PCI_MASTER_KEY` is delivered by compose interpolation — not `dotenv`, not `env_file:`

Two lines in the `app` service's `environment:` block (`docker-compose.yml:64-65`):

```yaml
      PCI_MASTER_KEY: "${PCI_MASTER_KEY:-}"
      PCI_MASTER_KEY_ID: "${PCI_MASTER_KEY_ID:-}"
```

Compose already reads `.env` for `${VAR}` interpolation, and this is the exact idiom the repo already uses for `MCP_PUBLIC_URL`, `PCI_PUBLIC_BASE_URL`, `HA_URL` and the three OAuth client ids. **No new dependency**: adding `dotenv` would mean a second delivery path with different precedence rules for the one variable in the product where "which value won" must be unambiguous, and a runtime that reads secrets off disk from the process's CWD. `env_file:` was rejected too — it makes `.env` a *required* file and silently changes precedence against `environment:` entries.

`PCI_MASTER_KEY_PATH` is deliberately **not** plumbed through: the container path is fixed by the `pci_master_key:/app/.pci` volume, and letting an operator repoint it would move the key out of the volume that persists it — a footgun with no upside.

### D2 · Boot is fail-closed on a vault the resolved key cannot open, with no bypass of any kind, and an empty vault passes

`assertVaultOpens()` (`src/bootstrap.ts:45-54`) runs in `main()` immediately after `runMigrations()` and before any edge serves (`src/index.ts:132`). It calls `assertVaultKey()` (`src/secrets/verify.ts:165`), which picks **one representative row per distinct `key_id`** and attempts a raw `aeadOpen` with the key `keyById` resolves for that id. A key that opens one row of a `key_id` opens all of them, so one open per key id is a complete check at O(number of key ids) — typically 1, and correct across a partially-completed rotation where the vault legitimately holds two.

Three properties are load-bearing and may not be softened without a new ADR:

- **No bypass exists.** There is no env var, no config field, no CLI flag, no argument. `assertVaultOpens()` takes none. `VaultVerifyOptions` (`keyIds` / `refs`) can only *narrow* the scan, is `undefined` in production, and is unreachable from `process.env`. `PCI_TEST_DB=1` is this repo's standing lesson (ADR 0015) about what an escape hatch costs once it exists; do not add an equivalent here.
- **An empty vault passes, structurally.** "Nothing to check" and "checked and passed" take the *same* branch by construction: `failures` is built from the scanned rows and the throw is `if (failures.length > 0)`. The forbidden shape is `if (!openedAtLeastOne) throw` — that would brick every genuine first run. `verify.db.test.ts` pins it with a named mutation.
- **The check is read-only.** `src/secrets/verify.ts` contains no `insert`/`update`/`delete` — asserted by a source-level test. It takes no `AuthContext` because it returns no user data, only counts, key-id labels and opaque refs; that exemption is documented in the file so a later reviewer does not re-litigate it.

The gate is wired in `src/index.ts` and **never** inside `startPushConnectors()`, whose surrounding `try/catch` would convert a fail-closed gate into a swallowed log line. `src/index.boot.test.ts` pins the call order `migrate → vault-gate → rest → push` and that a gate rejection propagates out of `main()`.

### D3 · The scope is secrets reachable from a credential with a live connector — nothing wider

The scan is not `from secrets`. It is `where ref in (…)` over `LIVE_SECRET_REFS` (`src/secrets/verify.ts:85-91`):

```sql
  select unnest(array[pc.secret_ref, pc.refresh_ref, pc.client_app_ref])
    from provider_credentials pc
   where exists (
     select 1 from connectors c
      where c.credential_id = pc.id and c.status <> 'revoked'
   )
```

The gate's purpose fixes its scope: a sync runs *per connector* and opens *that connector's* credential, so the rows whose failure actually produces the later `SecretAuthError` are exactly the rows a live connector depends on. Narrow enough to ignore rotation orphans and test artifacts; wide enough to catch the real disaster — a restored or migrated box whose key opens nothing, which fails here on every real credential at once. A revoked credential already has its refs NULLed by `revokeCredential`, so it drops out naturally. **The section below is why this scope, and not either of the two obvious wider ones.**

### D4 · The un-acknowledged-key banner prints on every boot, not once at generation

`vaultBackupNotice()` (`src/secrets/key.ts:193`) returns a banner whenever custody is `file`, the key exists, and no acknowledgement marker sits beside it; `assertVaultOpens()` writes it to **stderr** once per process, after the verification passes. stdout is the MCP protocol channel — one stray write there corrupts every local agent session. The banner is never printed after a gate failure: handing the operator a reassuring "your key is here" line on the exact boot where the key is wrong is worse than silence.

The acknowledgement marker is `` `${config.secretsKeyPath}.backed-up` `` (mode 0600), written beside the key *inside the same volume* on purpose — if the volume is gone the key is gone too, so there is no second piece of state that can drift. `vaultKeyStatus()` never calls `activeKey()`: reading status must not create a key.

An un-backed-up key is a standing, unbounded, unrecoverable data-loss risk. A per-boot banner is a proportionate price, and the noise is itself the pressure to ship the Console affordance that lets the operator acknowledge it (#97 item 3, front-end half).

### D5 · `""` is normalised to absent for `PCI_MASTER_KEY*`, and deliberately NOT for `DATABASE_URL`

`"${VAR:-}"` delivers an **empty string**, not absence, when the operator sets nothing. `src/config.ts` therefore reads the three `PCI_MASTER_KEY*` variables through `envOrUndefined()`, which maps `""` → `undefined`. Without it, `PCI_MASTER_KEY_ID=""` is not nullish, so `config.masterKeyId ?? "env"` stops defaulting and every credential gets sealed under `key_id = ''` — self-consistent at seal time, silently divergent from the rotation runbook, and a booby trap for the next operator who tidies the variable away.

`databaseUrl` keeps its expression verbatim: `process.env.DATABASE_URL ?? "postgres://pci:pci@localhost:5432/pci"`.

**The asymmetry is the point, and it is not an oversight.** The two variables fail in opposite directions. For the key, `""` normalised to absent lands on the *safe* default (generate/persist a key, and the fail-closed gate then checks it); left as `""` it lands on a wrong, silently-divergent key id. For `DATABASE_URL`, `""` left alone is a **loud connection failure**; normalised to absent it would fall through to the built-in default and silently connect to the **live `pci` database** — which is the exact shape of the 2026-06-17 incident that wiped ~700 finance rows and produced ADR 0015. A "helpful" normalisation there converts a crash into a data-loss event. Both `src/config.ts:6-8` and `src/config.test.ts` carry this reasoning, and the test asserts `config.databaseUrl === ""` specifically so a future tidy-up cannot quietly make the two symmetric.

### D6 · The fail-closed error message is the template for fail-closed errors in this repo

`assertVaultKey`'s message (`src/secrets/verify.ts:171-186`) names the exact `key_id` and the first failing opaque `ref`, counts the rows behind it, leads the remedies with **"Check `PCI_MASTER_KEY_ID` FIRST"** (a diverged *label* is now the likeliest way an operator meets this refusal — the key can be perfectly fine), gives the Docker-volume-vs-host-file trap by path, repeats the `down -v` warning, and ends with **"Nothing was modified."** It carries counts, key ids, opaque refs and file paths — and nothing else: no key bytes, no plaintext, no ciphertext, no AAD, pinned by a leak test.

That wording is why the production incident below was diagnosed in minutes rather than hours. **A fail-closed error in this repo names the exact value to restore, the most likely benign cause first, and whether anything was written.** Refusing to start is only half the feature; the other half is that the refusal is self-diagnosing.

## The incident: this gate refused to boot production, and the scope was wrong

The gate's **first real deploy bricked the production box** on 2026-07-25. Rolled back within minutes; the box was healthy throughout and nothing was modified. Fixed the same day, mutation-proved both ways, and re-deployed with every connection force-syncing `ok:true`.

**What went wrong.** The scan as first written was a bare `from secrets` — the assumption being that every sealed row belongs to a working credential. On a real long-lived deployment that assumption was **wrong by 64 rows out of 74**. `secret_ref` is overwritten on every credential re-paste, OAuth re-consent, iCloud re-onboard and Plaid re-link **without retiring the previous blob** (a known defect, deferred that same morning as #105 item 1), so a six-week-old vault accumulates orphans sealed under the key ids of past rotations (`rt-old-…`, `rt-new-…`, `k_…`). Note the reason code: nothing failed to *decrypt*. **No key resolves those ids at all** — every orphan raised `no_key`, and the gate correctly refused to start for a vault that was, for every purpose the product has, completely fine.

**The first narrowing was also insufficient**, and the production vault proved that too. Scoping to "referenced by any credential" still failed: a leftover `rotatetest-<uuid>` credential — debris from a rotation test, created 2026-06-17, with zero connectors and invisible to the Console — still referenced a row under a dead `rt-new-…` key id. It can never break a sync, and it would still have bricked the boot. (It and its orphaned secret were later deleted from the production box under explicit approval: credentials 8→7, secrets 74→73, connectors untouched.)

**The durable decision: a fail-closed gate is only as good as its scope.** A gate that refuses on a condition *wider* than the failure it exists to prevent is not conservative — it is a new failure mode, and one that fires at the worst possible moment, on upgrade, before anything is serving. Scoped as first written, this gate would have bricked **every beta user with any rotation history**, not just this one deployment. The rule that follows: **a fail-closed gate must be scoped to exactly the state whose failure produces the harm it names in its own error message.** This one names `SecretAuthError` at sync time, so its scope is the secrets a sync actually opens — no wider.

**And the honest reading of "the box verifies a design, never decides one."** No unit test, no local database and no amount of review could have produced a six-week-old vault carrying 64 rotation orphans under three generations of key ids. Only a real long-lived deployment had that data shape, and it is the cleanest instance of the principle we have. But the corollary matters as much and is easier to miss: **the design error was general, and the box merely revealed it.** "Every sealed row belongs to a working credential" was a wrong assumption about *all* users' vaults; that box was simply the first one old enough to disprove it. The lesson is not "test on prod" — it is that a gate over accumulated historical state must be specified against the state's *history*, not against the clean shape a fresh test database has.

## Alternatives considered

- **Warn on boot instead of refusing (log a loud line and serve anyway).** This is precisely the status quo the check replaces, one step louder. A gateway that boots green with an unopenable vault serves a healthy Console, reports connections as fine, and fails per-connection weeks later at sync time with an error whose cause is a Docker volume the operator last thought about at install. The whole value is collapsing that distance to zero. A warning in container logs nobody reads is what the one-shot key notice already was (D4), and its failure is the reason D4 exists. Rejected.
- **An environment-variable bypass (`PCI_SKIP_VAULT_CHECK`) for the operator who "knows it's fine".** Rejected outright, and this repo has the receipt: `PCI_TEST_DB=1` is a full bypass of the test-DB guard (ADR 0015) and lives in `CLAUDE.md` § Gotchas as a permanent hazard note precisely because a documented escape hatch is eventually used by someone who is wrong about being fine. There is also no legitimate use: the only states the gate rejects are "your key is wrong" and "your key's label diverged", and both have a real fix that the error message spells out. Anything a bypass would unblock, a *correct scope* unblocks properly. Note the shape of the alternative history — had a bypass existed, the production incident would have been "resolved" by setting it, and the wrong scope would have shipped to every beta user.
- **Check lazily, at the first secret open (today's pre-#97 behaviour).** Cheapest, and genuinely precise — it only ever fires on a credential something actually needed. But it fires in the sync runner, per connection, asynchronously, hours or weeks after boot, where it is classified as a sync error and surfaces as a broken connection rather than a broken *installation*. It also cannot say "nothing was modified", because by then things have been. Boot is the only moment where the answer is both known and free to act on. Rejected as the primary check — it remains as the natural backstop it always was.
- **Scope: every row in `secrets`.** The originally-specced and shipped scope. Rejected by production: on a real long-lived deployment, 64 of 74 rows are rotation orphans no credential references, and no key resolves their ids. It answers "is every blob this vault has ever held still openable?" — a question about the *vault's history*, not about whether the gateway can work.
- **Scope: every row referenced by any credential.** The obvious correction, and also rejected — by the same vault, one step later. A credential with no connector (a rotation-test artifact, a half-finished onboard, a stale row) references secrets that no sync will ever open, so its dead key id cannot cause the harm the gate names. It would still have refused the boot.
- **Fail the boot only when *no* key id opens anything (a "the whole vault is dead" heuristic).** Tempting, because it is immune to orphans. Rejected: it goes silent on the partially-broken case that is more likely in practice — a rotation that stopped halfway, or one credential sealed under a key that is gone — which is exactly the state the operator most needs named before it becomes a mystery sync failure. Correct scope beats a fuzzy threshold.
- **A `dotenv` dependency for key delivery.** Would fix the delivery gap in the app rather than in compose, but adds a second precedence model over the one variable where ambiguity is least acceptable, makes the runtime read secrets from a file relative to its CWD, and does nothing that two compose lines do not already do. It also has an active failure mode: a repo that ships both would let an operator "fix" delivery in `.env` while compose stays broken. `src/secrets/packaging.test.ts` asserts `package.json` contains no `"dotenv"` for exactly that reason. Rejected.

## Consequences

- **A restored, migrated or re-keyed box now refuses to start** instead of serving green and failing weeks later. `docker compose down -v` remains catastrophic — but it is now catastrophic *loudly, at the next boot*, with the remedy in the error text. `CLAUDE.md` § Gotchas' master-key bullet gained this clause.
- **Setting `PCI_MASTER_KEY` after the vault already holds rows sealed under an autogenerated key makes the gateway refuse to boot.** That is the gate working, not a regression. `.env.example` says to set it **before first boot**.
- **A diverged `PCI_MASTER_KEY_ID` is now the most likely way an operator meets the refusal** — the key is fine, only its label moved. Hence the remedy ordering in D6. Related trap, closed in the same wave: `.env.example` must never carry a comment on a variable's own line, because compose's dotenv parser strips a trailing comment *only when a value precedes it*, so `# PCI_MASTER_KEY_ID=   # optional label` would deliver the literal comment text **as the key id** and seal every credential under it. A packaging test scans every variable line for that shape.
- **Every variable documented in `.env.example` is now mechanically required to be delivered to the app container.** The test derives the set from the file rather than a hardcoded list, so the original defect class — a documented knob that reaches nothing — cannot come back silently for any future variable.
- **The `vaultKeyStatus()` / `acknowledgeVaultKey()` / `vaultBackupNotice()` seam is frozen** for the Console first-run "back up your vault key" card (#97 item 3, front-end half). Until that ships, the only ways to acknowledge are the exported function or `touch <keyPath>.backed-up`, and the banner prints every boot until then — by design.
- **Not closed by this ADR: retiring superseded vault blobs — #105 item 1.** This is the defect that *produced* the 64 orphans, and it is still live: `secret_ref` is overwritten without deleting the previous blob at `src/rest/admin.ts:172` and `:253`, `src/rest/oauth-routes.ts:269`, `src/oauth/refresh.ts:135`, and `src/connectors/plaid.ts:560-564`. The seam already exists and already ships — `deleteSecret(ref)` at `src/secrets/index.ts:43-45` — and the pattern to copy is `src/oauth/provider-apps.ts:113-120`: read `prior` before the upsert, then best-effort `deleteSecret(prior)` when `prior !== newRef`. Do **not** add a second sealing helper for it; an uncalled second API is worse than none. Until it lands, every user's vault keeps accumulating unopenable orphans — harmless to the gate now that D3 scopes past them, but real storage of dead ciphertext and a standing trap for any future tool that scans `secrets` naively. **Any such tool must adopt D3's scope or state why it does not.**
- **Boot cost is one small read-only query plus one AEAD open per distinct in-scope key id** — typically one, two mid-rotation. It runs after migrations and before any edge binds, so it adds nothing to the serving path.
- Unchanged by this ADR: online key rotation, multi-key active sets, and KMS/HSM custody. `src/secrets/rotate.ts` and ADR 0011 stand as they are.
