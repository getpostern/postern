# ADR 0035 — Public exposure is a supported, hardened path; loopback is the permanent OAuth redirect origin

**Status:** Accepted 2026-07-25 · **Date:** 2026-07-25 · **Closes:** the two decisions owed on #102 · **Supersedes:** ADR 0024 §D3 (Funnel as a warned fallback) and ADR 0024 §Consequences line 30 (edge hardening "filed, not blockers") · **Qualifies:** ADR 0025 (zero-exposure beta promise) · **Research:** 8-agent sweep 2026-07-25 (repo auth inventory · provider redirect rules · Tailscale constraints · cloud-MCP-client requirements · synthesis · 3 adversarial refuters), every code claim re-verified before acceptance.

**Numbering note:** 0033 and 0034 are RESERVED for the two ADRs owed at the time (vault fail-closed boot; sync classification + session revocation). This ADR deliberately takes 0035 rather than renumbering them.

## Context

ADR 0024 made `tailscale serve` (tailnet-private) the blessed remote-access story and treated Funnel — real public-internet exposure — as an explicit, warned, opt-in fallback, "only justified when a specific consumer needs public reachability." It then filed the edge hardening that public exposure would require (no bearer expiry, **no rate limiting on any edge**, cached-session survival) as "not blockers," with one sentence conceding that "public exposure via Funnel would [worsen these] — the Funnel recipe references them as prerequisites for anything beyond a demo."

Two things have changed since.

**The specific consumer turned out to be the main one.** ADR 0029 shipped the OAuth bridge precisely so hosted clients can authenticate, and #47 verified claude.ai connects and works. A user with a Claude or ChatGPT subscription connecting their own gateway as a custom connector is not a niche justified by exception — it is a primary reason to run Postern at all. A "warned fallback" framing makes the product's headline capability feel like something we tolerate.

**The deferred hardening is not theoretical.** A 2026-07-25 adversarial pass found six defects on the bridge edge, each verified in code. The two that decide this ADR: rate limiting **does not function at all** behind a tunnel (`clientIp()` reads `req.socket.remoteAddress`, which behind Funnel is the local daemon's address, collapsing every per-IP bucket to one global bucket), and an anonymous stranger can **permanently lock the owner out of their own connector** (`CLIENT_CAP = 50` is global and refuses rather than evicts, while claude.ai registers a fresh client on every connection). Shipping Funnel as documented today would publish those.

The ruling that settles it: the public-access rules themselves do not change, but whatever security hardening public exposure requires must be specced and implemented — because we cannot refuse a user the ability to connect their own gateway to claude.ai or chatgpt.com.

## Decision

**D1 — Optional public exposure is a first-class supported path, not a warned fallback.** ADR 0024 §D3's stance is superseded. Funnel-on-`:443` fronting the MCP edge is a supported configuration with a runbook recipe, a Console surface, and the same verification standard as any other shipped path. The warnings become *informed consent at the moment of enabling*, not a reason to discourage.

**D2 — "Zero REQUIRED public exposure" survives intact and stays a beta promise.** ADR 0025 is qualified, not overturned. A user who never enables exposure gets a gateway that is byte-identically loopback-only. **The PROMISE is the invariant.** The mechanism, current as of U4 `console-exposure-surface` (merged 2026-07-26): **`MCP_PUBLIC_URL` unset AND no stored `gateway_exposure` row ⇒ `resolveBridgeConfig` returns no config ⇒ every bridge path 404s** (`src/mcp/http.ts:109`, `:257-258`) and `resolveBridgeToken` never consults the bridge tables (`src/mcp/oauth-bridge.ts:733`). Verified live on a real deployment 2026-07-26 with the bridge off: the discovery document 404s and the `/mcp` 401 carries no `WWW-Authenticate` challenge. Any unit that changes how the bridge's config is resolved MUST update this sentence in the same merge — a stale mechanism here reads as a broken promise. **Exposure is never a default, never a nudge, and never a side effect of another setting.** The promise is "you never have to," not "you never may."

**D3 — The hardening is a build item and a gate, not a follow-up.** ADR 0024 §Consequences line 30 is superseded: those items are no longer "filed, not blockers." Every defect below is a **prerequisite** — no public-exposure path ships until they close. `src/mcp/oauth-bridge.ts:89`'s own comment (`#48 supersedes`) records the deferral; this ADR ends it.

1. **Real client identity behind a proxy.** `clientIp()` (`oauth-bridge.ts:166-168`) is the sole source and parses no forwarded headers; `grep` finds no XFF or PROXY-protocol handling anywhere in `src/`. Behind Funnel *and* behind Docker's `127.0.0.1:8788:8788` publish, `registerBuckets` and `authorizeBuckets` each collapse to a single global bucket — the limiter throttles the legitimate owner and an attacker identically. **Rate limiting that cannot distinguish callers is not rate limiting.**
2. **Registration must evict, not refuse.** `CLIENT_CAP = 50` (`:89`, checked at `:595`) is global; claude.ai registers a new client per connection. A stranger fills the table and the owner is permanently refused. **This is a denial of service against the owner, by someone holding no credential.**
3. **The public port must not starve the private one.** `POST /token` has no `takeToken` and opens a pooled transaction per request. Both edges run in ONE process sharing ONE pool (`src/db.ts` `max: 10`, `connectionTimeoutMillis: 10_000`; `src/index.ts` starts both). Unauthenticated public requests can therefore exhaust the pool the **loopback admin edge** depends on. Port separation defends the admin *routes*; it does not defend their *liveness*.
4. **Approval must not be aimable at the admin surface.** `redirectUriMatches` (`:192-211`) ignores the port for loopback hosts, requiring only path/query/fragment/userinfo equality, and `isRegistrableRedirectUri` (`:175-185`) accepts `http://` on any loopback port. A registered `http://localhost:1/api/export` therefore matches a presented `http://localhost:8787/api/export` — turning approval into a confused deputy aimed at `localOnly` routes, while ADR 0029 §7's anti-phishing display shows destination host `localhost`, which reads as *safe*. The port-blindness exists for a real reason (Claude Code declares ephemeral ports); the fix must preserve that without admitting arbitrary paths.
5. **Denial audits must not evict real ones.** `auditBridgeDeny` (`:413-422`) is unthrottled, and the audit queue is bounded and drops the OLDEST on overflow (`src/audit/queue.ts:53`), so sustained anonymous denials **evict genuine audit rows** — an integrity failure in the one surface that is supposed to be detective. **Correction (2026-07-25, found by the U2 spec author, verified): the defect is LARGER than first drafted.** This item originally read "runs BEFORE the rate check (`:628-640` precede `:648`)" — but `:648` is the first line of `authorizePostHandler`, a **different handler**. `authorizeGetHandler` (`:620-645`) calls `takeToken` **not at all**: `GET /authorize` is entirely unmetered today, and its three unthrottled `auditBridgeDeny` calls are reachable at line rate by an anonymous flood with no credential. The substance stands and widens; only the line attribution was wrong.
6. **A key handed to a cloud client must carry an expiry.** The knob shipped in #47 and is optional; for cloud-facing keys it becomes required.

**D4 — Loopback is the permanent OAuth `redirect_uri` origin, and it is a DIFFERENT setting from the public MCP origin.** Two settings by design, never unified.

- `PCI_PUBLIC_BASE_URL` (default `http://localhost:8787`) answers *"where does the operator's own browser land coming back from the provider."* Already pinned and Host-independent since ADR 0014 (`src/rest/oauth-routes.ts:96-107`, `_ctx` explicitly unused).
- `MCP_PUBLIC_URL` answers *"where does a vendor's server fleet reach this box"* — necessarily public HTTPS on `:443`.
- **No single value serves both** in the two-candidate space we actually have: a value public enough for a cloud fleet is one Google will refuse. (A user-owned domain *could* satisfy both — the two-settings conclusion rests on lifecycle, not impossibility: one is a zero-config default identical for every user on earth, the other is per-box. `PCI_PUBLIC_BASE_URL` remains a knob, so a BYO-domain self-hoster may unify them deliberately.)

**D5 — A `*.ts.net` name is NEVER the OAuth redirect origin.** Not discouraged — structurally impossible for Google, and non-generalizing for the rest. Google requires each redirect URI's domain to be a registered *Authorized domain*, which requires Search-Console **DNS-level** ownership verification (a TXT record at the registrar; a URL-prefix/HTML-file property is explicitly not accepted). Tailscale controls the `ts.net` zone and `ts.net` is on the Public Suffix List, so **both** branches dead-end: the user cannot publish a TXT record at their tailnet apex, and the ICANN-subset reading names a domain only Tailscale could verify. Google's policy independently binds: *"Only use redirect URIs … that refer to domains that you own."* A tailnet name is not a domain the user owns. **Binding invariant — no future agent may reopen this.**

**D6 — Whole-port Funnel on the MCP edge is the precise exposure shape, and it is load-bearing that no bridge route ever moves to the REST edge.** "Expose only `/mcp`" is not achievable: a vendor's fleet must anonymously fetch the discovery documents, `/register` and `/token` **before any credential exists**, so a path-scoped Funnel makes the OAuth flow impossible. But the MCP edge is a separate HTTP server on a separate port whose entire route table is eight routes (`oauth-bridge.ts:962-971` + `/mcp`; every other path 404s — `src/mcp/http.ts:253-256`), so taking the whole port exposes **exactly** the required set and nothing more. **Corrected 2026-07-25** (the original drafting said "four static JSON" and, by miscounting, silently dropped `GET /authorize` — the error propagated into the runbook before review caught it there). The eight are: **three** static JSON carrying no user data (two protected-resource documents + the authorization-server document); `/mcp`, bearer-gated; `GET /authorize`, which renders the approval page and requires an already-registered `client_id`; `POST /authorize`, **the agent-key login**; `POST /token`, needing a valid single-use code bound to a PKCE verifier; and **one** unauthenticated write, `POST /register` (D3 item 2). This is a consequence of ADR 0029 §3's choice to site the bridge on the MCP edge — **recorded as load-bearing so no later tidy-up moves a bridge route onto `:8787` and silently converts a precise exposure into a catastrophic one.**

**D7 — No second login, because the login already exists.** `POST /authorize` validates the pasted agent key through the same `resolveBearer` path as every other agent (ADR 0029 §2). Anonymous `curl` cannot pass it. Adding auth *in front* of the Funnel is not merely unnecessary but **impossible** — the vendor fleet fetches `/register`, `/token` and discovery with no credential and no browser, so anything in front makes the connector permanently unconnectable. Authentication must live inside the protocol, and it does. This resolves #102's "Funnel vs the admin surface" fork: **they are not incompatible — they are on different ports, and the REST edge is never funnelled.**

**D8 — The `funnel` node attribute recommendation is rescoped, not dropped.** ADR 0024 §D3 advised denying the attribute to `autogroup:member`. With Funnel now the blessed cloud path that would deny the supported configuration. The correct rule: **scope the attribute to the gateway node's tag**, which still prevents a mistyped `tailscale funnel` on any *other* node. (§D3's recommendation is easy to leave unapplied — a default tailnet CapMap grants `funnel` broadly.)

**D9 — Postern does not require its own tailnet identity in V0.** A Tailscale sidecar (its own node, own name, own `:443`) would solve the port collision that any user with an occupied `:443` hits — Home Assistant, a NAS panel, Plex — and would let the Console display the gateway's address instead of the user hand-copying it. It is **filed as a later convenience, not V0 and not a default.** It does not remove the irreducible setup (a Tailscale account, authenticating the node, and enabling MagicDNS + HTTPS certificates — all tailnet-wide settings only the user can change in Tailscale's own admin console), and shipping a second network identity into a user's private network by default is a bigger claim on their trust than the convenience earns. **Documented manual path first.**

## Consequences / follow-ups

- **Four units.** U1 one-origin (`redirect_uri` end-to-end) ‖ U2 public-edge hardening (the D3 gate) → U3 the `:443` endpoint documented → U4 the Console exposure surface. U1 and U2 own disjoint files and run in parallel; U3 and U4 depend on both.
- **#48 is no longer a deferral** — its content is U2, and `oauth-bridge.ts:89`'s `(#48 supersedes)` comment is discharged there.
- ADR 0024 §D3 and §Consequences line 30 are superseded by D1/D3 above; §D2's invariants (**the tailnet hostname goes in `REST_ALLOWED_HOSTS` never**; a fronting proxy must forward the original Host) are UNCHANGED and still bind. §D5's rejection of Cloudflare is UNCHANGED and still binds — Funnel is chosen partly *because* TLS terminates on our node.
- **Correction to ADR 0024's 2026-07-21 postscript:** its claim that the port-443 finding is "corroborated by the Claude connectors troubleshooting docs' non-443 port cause" is not supportable — Anthropic documents no port restriction. The *finding* is real (our own 2026-07-21 experiment; independently reported by practitioners in the same terms) but it is **vendor-undocumented, and may change without notice in either direction.** U3 fixes the citation.
- **A known cost of BYO-app OAuth with Google, not fixed here:** Google expires refresh tokens after 7 days for projects left in "Testing" status with sensitive scopes, so you re-consent weekly until you publish the app. Postern is BYO-app per ADR 0014, so every user's project starts there and every Google user re-consents weekly. **ADR 0002 predicted exactly this** ("BYO app in Google Testing → refresh tokens die after 7 days; doesn't scale") and ADR 0014 shipped BYO anyway; the onboarding spec parked it as out of scope. For a beta with real users it cannot stay parked. The fork was — instruct every user to publish their own project and click past an "unverified app" warning, versus revisiting ADR 0002 for one verified Postern app per provider (which makes us the OAuth client and changes the trust story). **RULED 2026-07-25: neither, for now — this ships as a KNOWN ISSUE.** BYO-app per ADR 0014 stands, Google users re-consent weekly, and we say so plainly rather than pretending otherwise. Rationale: both fixes are worse than the disclosure at this stage — publishing instructions add a multi-step Google Cloud detour to onboarding for a warning the user will meet anyway, and one verified Postern app per provider is a trust-story change that deserves its own ADR rather than being smuggled in as a beta workaround. **What this obliges us to do, and what a future agent must not quietly drop:** the Console must detect a Google refresh failure and say "re-consent needed" rather than surfacing a silent error (already specified in the onboarding spec, still unbuilt), and the seven-day expiry must be stated where a user connects Google — not buried in a runbook. Revisit if beta feedback shows it drives people off Google entirely.
- CT-log note reaffirmed and strengthened: tailnet HTTPS publishes the machine name to a public ledger. Hostname obscurity has **zero** security value — a partial `%.ts.net` CT query returns hundreds of node FQDNs across hundreds of tailnets. Assume any enabled endpoint is discovered within hours; that is an argument for D3, not against exposure.
- `CLAUDE.md` gains one clause: public exposure is supported and opt-in per this ADR, and the D6 invariant that no bridge route may move to the REST edge.

## Addendum 2026-07-28 — §D1: the public address is a BARE ORIGIN (#126, `bridge-address-origin-guard`)

The saved public address (Console `gateway_exposure` row or `MCP_PUBLIC_URL`) is a bare `https://` origin — never a path, never userinfo. A path-carrying value (including the `/mcp` URL the Gatehouse card displays, the most natural paste) previously validated, then made the bridge advertise authorization/token/registration endpoints that 404 on the gateway itself with every health signal green — found live 2026-07-27 connecting claude.ai. Both are now refused at the ONE validator with messages naming the corrected origin; an older-build row carrying a path resolves to bridge-OFF + `db_invalid` (fail-closed, legible), and a structural test asserts every URL in the discovery documents — including the 401 `WWW-Authenticate` challenge — is routed by the live edge, method-aware, over a document list derived from the route map. Fronting the gateway *under a path prefix* behind a rewriting proxy is explicitly unsupported: it never worked, and now the gate says so. Merged 2026-07-28.
