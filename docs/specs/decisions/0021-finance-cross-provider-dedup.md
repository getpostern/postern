# ADR 0021 — Cross-provider finance dedup: deterministic within-sector enriched union, served as a 3-row synthetic-union (in V0)

**Status:** Accepted · **SHIPPED and DEPLOYED** 2026-06-28 (a 5-part cluster #34a/#34b/#33/#30/#32, suite 1066 green) — **live-verified on a real deployment** (sync-now ran `reconcileFinance`: each cross-provider pair collapsed to one served account, both provider rows shadowed behind a synthetic winner, and their overlapping transactions shadowed alongside; balance-tuple co-selection confirmed — the served row carries one member's (balance, real date) pair; no double-count). The 3-row synthetic-union shape superseded the earlier 2-row "materialize-into-winner" detail after a data-model study of a real two-provider dataset. (Built in parallel and reviewed before merge; #34b's same-provider txn double-count and #33's account-less-connector visibility were caught in review and fixed before merge.)

## Context

Dogfooding real finance exposed a structural problem the gateway had deferred. The same real-world account/card can be connected through **two providers at once** — the observed case: two cards at the same issuer, each connected via BOTH Plaid (richer enrichment, ~recent 30 days) AND SimpleFIN (months more history, the free default). The cache faithfully stores both, so the agent and Console see **duplicate accounts** and an agent summing balances/spend **double-counts**. Two distinct defects surfaced (#34): (a) credit-card `current_balance` SIGN is not provider-normalized (Plaid stores credit as owed-POSITIVE while SimpleFIN stores the same card liability-NEGATIVE — fixed by #34a, which the data-model study calls "the single most important fix"); (b) no cross-provider dedup, which CLAUDE.md had filed entirely under deferred **chapter-2** work.

Two first-principles points shaped the design: (1) **the store should normalize and not keep duplicates** — and the live data confirmed the empirical half (a real two-provider overlap matched **every candidate transaction on (amount + posted-date) with zero conflicts**), so matching the same account/txn across providers is **deterministic, not fuzzy**; (2) **keep all the extra stuff** — i.e. a UNION of the best of both providers, because coverage differs (Plaid recent + richer; SimpleFIN deeper history). And the altitude rule (CLAUDE.md "Build for the world, not one box"): the design must be right for the long tail (investments, retirement, loans, charge cards, crypto, multi-currency), not merely safe — verified by an **E2E Plaid + SimpleFIN data-model study of a real two-provider dataset, covering every account on it**, which both validated the skeleton and forced the corrections below.

## Decision

1. **Deterministic within-sector cross-provider dedup is IN V0** — explicitly DISTINCT from the deferred chapter-2 work. *Within a single sector (finance)*, *exact-key* matching (no LLM, no fuzzy, no inference) is **normalization** — the same class as negating a Plaid amount. What stays chapter-2 is *cross-domain SEMANTIC* entity resolution (account ↔ email ↔ contact) and any `source_events`/`derived_facts`.

2. **3-row synthetic-union** (supersedes 2-row mutate-in-place). For each cross-provider dedup group the store holds THREE rows: **both provider rows kept PRISTINE** — each a faithful `normalize()` of its OWN `raw`, fully drillable, never mutated — and SHADOWED (`shadowed_by_id` → the winner); PLUS **one explicitly-SYNTHETIC winner row** (`source_object_id='union:<canonInst>:<mask>'`, `connection_id`=the winner-provider's, `raw=null`, `dedup_status='winner'`) whose normalized columns are the best-per-field composite. `query()` serves the synthetic winner and hides both shadows + the now-shadowed reals with ONE reversible `shadowed_by_id is null` predicate (folded into the partial indexes — single-provider users, the majority, pay zero); `getRecord`/`fetchLive` stay unfiltered so both real rows drill verbatim. `reconcileFinance(userId)` does diff-only CREATE/RECOMPUTE/DROP of synthetic rows from the current live set, in one transaction under a per-user advisory lock. **Why 3-row over 2-row:** mutating a real provider row's columns with another provider's values breaks per-row faithful-cache (the row no longer matches its own `raw`) and forces a pile of machinery (anti-poisoning, de-graft pass, re-enrich-after-sync transient window, lockstep-vs-a-real-row) that exists ONLY to manage that clobber — the synthetic row deletes all of it and keeps every real row byte-faithful. Reversibility is trivial: remove a provider → reconcile drops/recomputes the synthetic from the remaining pristine reals; a sole survivor un-shadows.

3. **The comparator (populates the synthetic winner) — one general rule, with two corrections from the study.** Per normalized column, select from the group members by: **(1) REAL-over-SYNTHETIC** (only `balance_at` has a synthetic axis, decided per-member by the provider-native policy constant `{plaid:true, simplefin:false}`); **(2) NON-NULL-over-NULL**; **(3) PROVIDER-RANK** (`plaid=0` < `simplefin=1`) then `source_object_id` then row `id` (a total order). Corrections: **(a)** `(current_balance, balance_at, balance_at_is_synthetic)` are **co-selected as ONE coherent tuple** from a single member (the balance_at winner) — serving Plaid's balance number stamped with SimpleFIN's timestamp is a false point-in-time assertion (the two providers report the same card's balance a few cents apart, which proves the numbers genuinely differ); in the observed overlap this serves SimpleFIN's (balance, real date) pair. **(b)** `available_balance` is **per-type** — trust SimpleFIN only for depository; for credit/loan/investment prefer Plaid or null (SimpleFIN credit `available` is garbage 0/negative); treat a Plaid charge-card `limit=0` as null. The synthetic only ever SELECTS a real member's value — no fabricated/computed value.

4. **Account key = exactly-4-digit `mask` + canonical institution (`org.domain`-primary) + currency-when-both + a coarse account-class guard.** Institution: prefer **`org.domain`** (present in SimpleFIN `raw.org.domain` — a registrable domain such as `examplebank.com` is far more stable than the display name; Plaid via institution_id→domain); name-fold + alias map only as fallback. Mask: require **exactly 4 digits both sides** (Plaid mask is "2-4 alphanumeric"; SimpleFIN via `/\((\d{4})\)\s*$/`, verified correct on every live account name in the study — names that carry no 4-digit mask, such as retirement accounts, non-numeric suffixes and some card products, yield no-mask and then fail open). Currency: match when both present. **Class guard** (account_type is a GUARD, never a key component): infer SimpleFIN class — `holdings.length>0 ⇒ investment` (robust), else name keyword, else AMBIGUOUS — and merge UNLESS the two classes confidently conflict (do NOT use balance-sign alone: paid-off cards sitting at zero would misclassify as assets); ambiguous ⇒ allow (preserves the same-issuer/near-zero-card dedup). Fail-open everywhere: any disagreement ⇒ a visible dupe, never a wrong merge.

5. **Transaction pass** (only within a cross-provider group): bucket by `(group, round(amount,2), posted-date within ±1 day, currency)`, **restricted to credit+depository groups** (investment txns are Plaid-invisible — `/transactions/sync` omits them), match SimpleFIN `posted` ↔ Plaid `date` (posting-to-posting), **exclude Plaid pending** rows. **N-to-N count-reconcile**: pair `min(N_plaid, N_simplefin)` per bucket; the leftover stays LIVE flagged `pending` (leading-edge) or `ambiguous` (count conflict) — never blind keep-one (two real same-day same-amount charges must not collapse to one).

6. **Holdings / investment transactions are OUT of V0 dedup.** SimpleFIN holdings live only in `account.raw` (up to 50 positions); Plaid holdings aren't fetched; investment transactions are Plaid-invisible. A genuine world gap → a **separate follow-up spec** (`finance.holding` table + Plaid `/investments/holdings` + `/investments/transactions`); this ADR states holdings are out so investments aren't assumed covered. (Investment *accounts* still dedup at account level, fail-open + class guard.)

## Consequences

- **Faithful cache is preserved cleanly:** every REAL row stays a faithful projection of its own `raw` (drillable verbatim); the served winner is an **explicitly-synthetic, deterministically-derived** row (`raw=null`) — every served field is `normalize()` of some real member's raw. This is a within-sector, exact-key, reversible SELECTION among real stored values = more normalization, NOT a chapter-2 derived fact. (The 2-row "composite columns on a real row" tradeoff is gone.)
- **Reads stay lightning-fast** — one `shadowed_by_id is null` predicate folded into the recreated partial indexes; single-provider users (the majority) are untouched. Read-time projection was rejected (it would tax the common path).
- **Schema (migration 0009):** `finance_accounts` += `mask`, `org_domain`, `shadowed_by_id`, `dedup_status`, `dedup_group_id`; `finance_transactions` += `shadowed_by_id`, `dedup_status`; synthetic rows allowed (`raw` nullable, `source_object_id='union:…'`); partial primary-time indexes recreated with the shadow predicate.
- **Named residuals (documented, not fixed in V0):** per-account cross-provider txn drill is incomplete (`account_source_id` not grafted; sector-wide aggregates correct; #33's mask-grouped view mitigates); a genuinely-ambiguous-class SimpleFIN account sharing a last-4 with a different-type account slips the class guard (guard blocks only on a CONFIDENT conflict); a transient Plaid-only pending dupe until it posts.
- **Untested-vs-Plaid live:** the only live cross-provider overlap was a single pair of same-issuer cards; institution-domain matching, the class/currency guards, and non-card txn matching have ZERO live coverage and must be proven by fixtures, not by one deployment's data.
- Supersedes the earlier ADR-0021 / cluster-spec "enriched-winner composite ROW" + "materialize-into-winner" framing.

Relates to: ADR 0004 (tombstones — the shadow marker is isomorphic), ADR 0018 (jsonb projection / drill), the finance neutral-floor discipline (CLAUDE.md), and the data-model study of a real two-provider dataset.

**Postscript (2026-07-11, unit `finance-dedup-trust-batch`):** the merge is now inspectable (`includeShadowed` opt-in drill-through with core-applied read-only linkage projection — deliberately NOT REGISTRY fields, which are also the ingest write allow-list), honest about uncertainty (maskless same-institution pairs flagged "possibly the same account" instead of silently double-counting), and correctable by ground truth (operator confirm-merge in its own `finance_dedup_confirmations` table — deterministic, reversible, audited, fail-open on hard conflicts; the no-guessing rule stands — a confirmation is proof, not inference).
