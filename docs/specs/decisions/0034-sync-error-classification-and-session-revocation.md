# ADR 0034 — Sync error classification and session revocation

**Status:** Accepted · **Date:** decided 2026-07-25, recorded 2026-07-26 · **Supersedes:** the ADR 0024 residual at `0024-remote-access-tailscale.md:30` — *"a revoked bearer's cached MCP session survives until its next initialize"* — which is no longer true and is no longer accepted · **Related:** #99, ADR 0016 (the `syncing` status this reuses), ADR 0023 (the freshness derivation this must not fork), ADR 0007 (the SDK contract that is the real fix), ADR 0029 (bridge sessions, covered for free)

## Context

Two defects that look unrelated and are the same defect: **the gate's own state ends up lying about what happened.**

**Sync classification.** `src/sync/runner.ts:424` treated *every* error that was not a `RetryableError` as terminal → `markError` → `connectors.status='error'` → `deriveFreshness` returns `error` (`src/core/freshness.ts:123-127`) → the Console renders "needs you / Reconnect". And `grep -rn RetryableError src/connectors/` hit **microsoft only**. So one 503 from Plaid, SimpleFIN, Whoop, Google or the OAuth token endpoint flipped a healthy connection to "needs you" until the next successful poll — a full cadence, which for finance is 6 hours. That asymmetry is the whole motivation, and #99 states the cost in the user's terms rather than the system's: **a false "needs you" twice is how a user stops believing the true one.** The gateway's only job on this surface is to say truthfully whether a source needs the human, and it was saying so on a network hiccup.

**Revocation.** `sessionAuth()`'s resolver (`src/mcp/bearer.ts:87-104`) re-checked only `ctx.expiresAt`, and `expires_at` is NULL by default (`src/rest/admin.ts:355-356,363`), so that branch was a permanent no-op. `resolveBearer` — the only thing that reads `revoked_at` (`src/auth/resolve.ts:61`) — ran exactly once per session, at `handleInitialize` (`src/mcp/http.ts:147`). The REST mirror, meanwhile, re-resolves the bearer on **every** request (`src/rest/mirror.ts:47-50`). **The two agent edges disagreed about what Revoke means**, and the Console had been written to word the weaker guarantee honestly rather than fix it (`apps/web/src/pages/agents/AgentsPage.tsx:269-271`: *"An in-flight session already resolved its grants and may finish; the next session is denied."*). ADR 0024 filed this as a known, accepted residual for a tailnet-private deployment. ADR 0035 made public exposure on `:443` a supported configuration; an operator verb that does not actually stop a live agent is a different proposition once the edge can be reached from the public internet.

## Decision

**D1 — Two classes, no third, decided by one runner-side function.** `classifySyncError(provider, err)` returns `"transient" | "terminal"` (`src/sync/retryability.ts:261`). Transient means "the connection is fine, the network or the provider hiccupped" and is retried in-run, then parked at `status='syncing'`. Terminal means "a human must act" and writes `status='error'` immediately, with **zero** retries. There is no `unknown`, no `degraded`, no third state — a third state would have to be rendered, and every surface that renders freshness is downstream of one derivation (ADR 0023).

**D2 — The precedence order is part of the contract, not an implementation detail.** The function returns on the first hit, in exactly this order:

1. `err instanceof RetryableError` → **transient**. The connector's explicit declaration outranks everything; this is how `microsoft` already worked and must keep working identically.
2. `SecretAuthError` → **terminal**. A vault that will not open is a dead credential (`src/secrets/index.ts:42`).
3. `ConfigError` → **terminal**. The provider app is not configured (`src/oauth/providers.ts:27`); no amount of retrying configures it.
4. `TokenEndpointError` (`src/oauth/exchange.ts:40-55`): the OAuth **`code` outranks the HTTP `status`** — `invalid_grant`, `invalid_client`, `unauthorized_client`, `invalid_scope`, `access_denied`, `no_access_token` are terminal *even when the response carried a 5xx*; only then does the status decide.
5. The provider's own declared `terminal` patterns.
6. Universal terminal vocabulary on the message — `unauthorized`, `forbidden`, `invalid_grant`, `revoked`, `ITEM_LOGIN_REQUIRED`, `INVALID_ACCESS_TOKEN`, `credential not found`.
7. Node network codes read from both `err.code` **and** `err.cause?.code` (`ECONNRESET`, `ENOTFOUND`, `EAI_AGAIN`, the `UND_ERR_*` family, …), plus `AbortError` / `TimeoutError` → **transient**.
8. The provider's own declared `transient` patterns.
9. Universal transient status vocabulary — the two anchored message shapes the fleet actually emits, `returned <status>` and `failed: <status>` — where the captured number must satisfy `isTransientHttpStatus` (`retryability.ts:145-147`: 408, 425, 429, and every 5xx).
10. Otherwise → **terminal**.

The order is load-bearing at three places specifically: **1 above 6** (a `RetryableError` whose message happens to contain "403" is still what the connector said it was), **4's code above 4's status** (a dead refresh token wrapped in a 503 must still read "reconnect me"), and **6 above 9** (`plaid transactions_sync failed: 400 ITEM_LOGIN_REQUIRED` is a re-link, not a blip). Reordering any of those three inverts a real user-visible outcome, which is why each has a named mutation in `src/sync/retryability.test.ts`.

**D3 — UNKNOWN IS TERMINAL, deliberately.** An error the table does not recognise is classified terminal and the connection goes to `status='error'`. This is the counter-intuitive half, so state the two failure modes plainly in terms of what the user sees. Erring **terminal** on an unknown error costs a false "needs you": the user opens the Console, sees Reconnect offered on a source that did not need it, and is annoyed — a **loud, visible, self-correcting** wrong answer that the next successful poll clears. Erring **transient** costs a permanent, silent "Syncing…": a genuine connector bug — a normalization failure, a schema drift, an unhandled provider response — retries three times, fails three times, parks in the quiet `syncing` state, and stays there **forever**, because the scheduler will keep re-polling it and it will keep failing, and no surface ever tells the user their data stopped arriving. A source that is quietly frozen while the UI says it is fine is the exact failure ADR 0023 was written after (a 2-week invisible outage). Loud-and-wrong beats silent-and-wrong here, and it is not close. "Declare rather than inherit" is enforced by the mandatory `note` field and the set-equality coverage test, **never** by making the default permissive.

**D4 — The message-vocabulary table is a BRIDGE; the SDK obligation is the fix.** `PROVIDER_RETRYABILITY` has one entry per provider registered by `registerConnectors()` (`src/bootstrap.ts:33-45`), each with a mandatory non-empty `note` citing its throw sites. It exists because **the connectors discard the cause**: `src/connectors/plaid.ts:237-239` is literally `catch { throw new Error("plaid ... failed: network error") }` and `src/connectors/google.ts:210-212` is the same, so for most providers **the thrown message is the only signal that survives**. Classifying on message text is string-matching another module's prose — it is fragile by construction, and it silently degrades the moment a connector reworders a throw. It is accepted here only because it is *closed* (a fixed table, not a heuristic), *cited* (every pattern names its throw site), and *mechanically complete* (a coverage test asserts set **equality** against the registry in both directions, so adding a connector to `bootstrap.ts` without a declaration fails the suite rather than inheriting a default). The durable answer is the **connector contract**: every connector throws `RetryableError` for its own transients, the way `src/connectors/microsoft.ts` already does, as a `CONTRACT_OBLIGATIONS` entry in `src/sdk/contract.ts` asserted by `src/sdk/conformance.ts`. When that lands, entries in this table are deleted rather than added. Until then, every ambiguous provider stays terminal and says so in its `note` — `simplefin`'s bare `"account fetch failed"` is thrown by *both* the network catch (`simplefin.ts:211-213`) and the malformed-access-URL branch (`simplefin.ts:193-196`); `"gmail: sync failed"` covers both a search failure (`gmail.ts:502`) and a bad app-password (`gmail.ts:625`); the iCloud DAV strings collapse network and 401 alike. **A residual that keeps a dead credential loud is the right residual.**

**D5 — Revocation on the MCP edge is a periodic-free, in-process SWEEP driven by the operator verb, not a per-call `revoked_at` read.** Every operator verb against an agent — mint/rotate (`postAgent`), grant change (`patchAgent`), revoke (`revokeAgent`), delete (`deleteAgent`) — calls `endAgentSessions(userId, agentId)` (`src/mcp/bearer.ts:121`), which evicts every cached session matching `(userId, agentId)` across every mounted edge and closes its transport. **Order is DB write first, sweep second**, always: sweeping before the write leaves a window in which a fresh initialize legitimately re-resolves the not-yet-revoked row. The opposite race — a session that authorized *before* the sweep and binds *after* it — is closed by a `revokeFence` (`bearer.ts:100`, 5-minute TTL): `bind(sessionId, ctx, resolvedAt)` refuses and returns `false` when a verb landed at or after `resolvedAt`, and the caller closes the transport without ever serving it. The sweep is chosen over the obvious alternative — re-reading `revoked_at` on every tool call, the way the REST mirror does — for two reasons. It is **bounded**: work is proportional to operator verbs (rare, human-paced) rather than to tool calls (hot, agent-paced). And it keeps **no DB round-trip on the read hot path**: the grant check stays an in-memory `Set` membership test (`src/auth/resolve.ts:6-9`), which is the "lightning fast" property the product is sold on. The MCP session map is bounded by `MAX_SESSIONS = 512` (`src/mcp/http.ts:33`), and a new initialize past the cap is **refused with 503 rather than evicting an existing session** — an MCP client legitimately holds one session for days (the `:443` claude.ai standing-access case), so LRU eviction would silently kill a working connection, and only an already-authenticated caller can reach the check, so refusing is not an anonymous DoS lever. **⚠️ Amended by [ADR 0037](0037-mcp-session-cap-reclaim.md) (2026-08-08):** production showed the map fills with *abandoned* hosted-client sessions until refuse-over-evict locks out every live caller (#147); at the cap a floor-gated reclaim of the single most-idle session (idle ≥ 1 h) now precedes the refusal. The refusal case, and everything else in this section, stand.

**D6 — Reads take the sweep; writes take the per-call check. The asymmetry is deliberate.** The memory-floor spec (ADR 0027) specs the opposite posture for the notebook's three write primitives: `writeMemory` / `updateMemory` / `deleteMemory` each re-read the caller's `agent_grants` row (`revoked_at` plus fresh `sectors`) on **every call**, before acting. That is not an inconsistency with D5, it is the same trade evaluated on different traffic. Reads are the hot path and are non-destructive, so they pay nothing per call and rely on the verb-driven sweep plus the bind fence. Writes are rare and irreversible (the notebook hard-deletes; there is no tombstone to recover), so a per-call SELECT is invisible in aggregate and a revoked agent's still-open session must not be able to tamper with the store even in the milliseconds before a sweep completes. Stated as one rule: **the sweep is how a revoked session stops reading; the per-call re-read is how a revoked session stops writing.**

**D7 — The ADR 0024 residual is reversed, not merely narrowed.** ADR 0024 §"Consequences / follow-ups" (`0024-remote-access-tailscale.md:30`) filed, as one of three accepted pre-existing gaps, that *"a revoked bearer's cached MCP session survives until its next initialize"* — with the note that tailnet exposure does not worsen it but Funnel would. **That is no longer the behaviour.** From the moment `POST /api/agents/:agentId/revoke` returns 200, the next tool call on an **already-open** MCP session is denied — no reconnect, no restart, no expiry required — and the same holds for a narrowed grant via `PATCH` and for a mint/rotate that replaces the key. `revokeAgent`'s 200 body gains `sessions_ended: number` so the operator is told how many live sessions the verb actually ended. Bridge-derived sessions (ADR 0029) are covered for free: `resolveBridgeToken` returns a ctx carrying the grant's own `agentId`/`userId` (`src/mcp/oauth-bridge.ts:256`), so they match the same predicate. **This ADR supersedes that specific residual of ADR 0024 and nothing else in it** — the other two items on that line (bearers had no expiry; no rate limiting on any edge) were addressed elsewhere, and §D2's invariants stand untouched. Downstream copy that documented the old weaker guarantee is now an understatement rather than a lie — including the two Console strings at `AgentsPage.tsx:269-271` / `AgentDetailPage.tsx:310-312`.

## The bug that proves the precedence order matters

Adversarial review of this unit turned up a **real production bug in another module**, and it is worth recording in full because it is the sharpest possible illustration of D2 and D3.

`SecretAuthError` (`src/secrets/index.ts:42`) declared **no `override name`**. An ES class extending `Error` inherits `name === "Error"`, so a real instance of `SecretAuthError` carried `.name === "Error"` — and precedence step 2, the rule whose entire job is to keep a dead vault loud, **never fired against a real instance**. What happened instead: a vault failure fell through to step 9, and if its message happened to carry a 5xx it classified **transient** → retried → `status='syncing'` → `deriveFreshness` returned the quiet state → **the Console never offered Reconnect.** A dead credential rendered as "Syncing…", permanently. That is the exact inversion #99 was filed to prevent, produced inside the fix for it.

It passed the suite only by accident of the step-10 default: a `SecretAuthError` whose message carries no status is terminal anyway, so every unit test of the rule was green for the wrong reason. This is the repo's signature defect — correct code behind a guard that cannot fail — and the only thing that caught it was running the mutation.

Both halves were fixed on 2026-07-25, in two different units of the same wave. The class now declares `override name = "SecretAuthError"` (`src/secrets/index.ts:42-44`, with a comment stating that the line is load-bearing and naming the classifier that depends on it), shipped by `vault-key-packaging`. And **the classifier no longer depends on that being true**: `namesOf(err)` (`src/sync/retryability.ts:210-216`) reads **both** `err.name` and `err.constructor.name`, because either alone is insufficient — a flattened error literal has no constructor, and a class with no `override name` has no useful `name`. Keeping the constructor read is what survives an error crossing a boundary that drops its prototype, or that `override name` being deleted again by someone who thinks it is cosmetic.

One process note belongs with it: the two units were **green apart and red together**, and it was fixed at the integrated gate. `backend-robustness` had asserted `expect(real.name).toBe("Error")` to *document* why its duck-type was necessary; `vault-key-packaging` fixed the class in the same wave and that assertion went red at the integrated gate. **A test may pin why a guard exists — never the bug that motivated it.**

## Alternatives considered

- **Classify unknown as transient ("be forgiving; most failures are blips").** Superficially the kinder default, and it would have made the false-"needs you" number go to zero. Rejected because it converts every unrecognised failure — including every genuine connector bug — into a permanent silent `syncing` row that no surface complains about, and the scheduler will re-poll it forever without anyone finding out. A wrong answer the user can see and dismiss is strictly better than a wrong answer that looks like the system working. See D3.
- **A per-call `revoked_at` read on the MCP read path** (parity with `src/rest/mirror.ts:47-50`). The simplest correct thing, and it is what the REST mirror does. Rejected for the read path because it puts a DB round-trip on every tool call and breaks the property that the grant check is an in-memory `Set` membership test (`src/auth/resolve.ts:6-9`) — the "lightning fast" tie-breaker. The MCP edge's traffic shape is different from the mirror's: an agent session issues many small calls in a burst. The read is not rejected *in principle* — it is exactly what the memory-floor spec (ADR 0027) specs for **writes**, where the call rate is low and the operation is destructive. See D6.
- **A periodic background sweep of the session map against the DB** (a timer that re-checks every cached ctx every N seconds). Rejected: it reintroduces the DB traffic without the per-call read's correctness, and it makes revocation *eventually* consistent with an N-second window during which the operator has been told the agent is revoked and it is not. The verb-driven sweep is instant and does strictly less work.
- **Retry with backoff inside each connector, instead of a runner-side classification taxonomy.** Every connector already knows what its own transients are, so this is where the knowledge lives. Rejected as the *mechanism* for two reasons. It is nine independent implementations of the same loop, with nine chances to get the budget, the jitter or the shutdown behaviour wrong — and the runner is the only place that knows whether a retry is still schedulable (an operator can pause or revoke mid-retry, which `stillSchedulable` checks between attempts) or whether the process is shutting down (the retry timer is `unref`'d so it can never hold `buildShutdown` open). More fundamentally, connector-local retry does not solve the *status write* — after the connector gives up, the runner still has to decide between `error` and `syncing`, which is precisely the classification this ADR exists to make. Note what is **not** rejected: connectors declaring their transients via `RetryableError` is D4's stated end-state. Declaration belongs in the connector; the loop and the status write belong in the runner.
- **Leaving the ADR 0024 residual in place**, on the grounds that it was already accepted, the Console words it honestly, and #99 itself downgraded it from a harsher finding. Rejected. An accepted residual is a judgement made against a threat model, and the threat model changed: ADR 0035 made public exposure on `:443` a supported configuration, and "Revoke does not stop the agent that is currently reading your mail" is a different sentence on a tunnel than on a tailnet. It is also the *cheapest* of the three gaps on that line to close — one in-process registry, no IPC, no DB channel, because `src/index.ts` `main()` starts the REST edge and the MCP HTTP edge in the same Node process. A residual that is both more dangerous than it was and nearly free to close is not a residual any more.
- **A session TTL or idle sweep, and LRU eviction at the session cap.** Rejected both: MCP clients legitimately idle for hours and hold a session for days, so a TTL expires working connections and LRU silently kills a standing claude.ai session at exactly the moment the box gets busy. A hard cap that **refuses the new session** is bounded and non-destructive. **⚠️ Half-superseded by [ADR 0037](0037-mcp-session-cap-reclaim.md) (2026-08-08):** the TTL/idle-sweep rejection stands; the at-cap half is amended to a floor-gated reclaim of the single most-idle session after #147's starvation incident.
- **Sweeping on `PATCH` only when the grant narrows.** Rejected: it requires diffing old and new sector arrays inside the route, which is a second place for grant semantics to drift, and the cached `grantedSectors` set is stale either way. One unconditional rule, at the cost of one re-initialize on a widening.

## Consequences

- A transient blip on any connector now costs at most `MAX_SYNC_ATTEMPTS = 3` attempts with jittered backoff (`src/sync/runner.ts:330-334`) and, if still failing, a quiet `status='syncing'` row carrying the masked reason in `last_error` — never a false "needs you". Both non-scheduler call sites already race `syncConnection` against a bounded wait (`src/core/context.ts:277-283`, `src/core/lifecycle.ts:507-512`), so the added retry time can never extend a user- or agent-facing wait; it extends only the background run.
- **A dead credential and a flaky network are now distinguishable in the connector row itself**: `status='error' + last_error` versus `status='syncing' + last_error`. That distinction is what the Console's Reconnect affordance keys off.
- **No new state and no migration.** The transient resting place is ADR 0016's existing `syncing` status, which the scheduler already re-polls (`src/sync/scheduler.ts:126`) and `deriveFreshness` already maps to the quiet state (`src/core/freshness.ts:128`). Inventing a second representation would fork the freshness contract, which `src/core/freshness.ts` owns as the ONE derivation.
- The retry re-runs the **whole** attempt including the connection-row load, because a `cursorCommittedThrough` connector persists its cursor mid-stream and reusing attempt 1's `ctx.cursor` would restart the delta chain from a stale checkpoint. Every upsert is idempotent by construction, so a partial attempt followed by a full one is safe.
- **`PROVIDER_RETRYABILITY` is a growing liability by design, and it is meant to shrink.** Every new connector must add an entry or the suite fails. That friction is the point — it is what makes the SDK obligation worth doing rather than something that stays permanently "next".
- The push paths are untouched: `ingestRecords` never retries and never flips status (the documented no-error-lockout behaviour), `home_assistant` never travels the poll path at all, and `apple_health` arrives by webhook. Their table entries say so.
- Both agent edges now mean the same thing by Revoke, which makes the operator verb honest enough to document as a security control rather than a best-effort one — a precondition for anything reachable from the public internet.
- Audit is unchanged: no audit write was added on the eviction path. Audit stays async and detective.
