# ADR 0024 — Remote access for self-host V1: Tailscale serve (tailnet-private) is the blessed story

**Status:** Accepted 2026-07-10 · **Date:** 2026-07-10 · **Closes:** #23 · **Research:** 4-agent sweep 2026-07-10 (Tailscale/Funnel state, alternatives, MCP-client matrix, live-probed exposure survey); the direction was pre-logged 2026-06-20 and confirmed 2026-07-10.

## Context

The gateway is loopback-only by design: the REST edge carries a class of admin routes whose ONLY authorization is reachability (`localOnly` Host-allowlist — mint-agent-key, export-everything, grantless data read, erase; `docker-compose.yml` states the threat verbatim). But two surfaces are DESIGNED for remote (device push-ingest with a per-connection 256-bit secret; the MCP edge with a scoped bearer) and a third is safe for it (the bearer-gated REST read mirror, per-request resolution, immediate revocation). Self-hosters need a documented answer to "how do I reach this away from home" that never widens the admin surface. A real long-lived deployment has run an improvised `tailscale serve` for weeks (ingest `:8443`, MCP `:10000`) — this ADR turns that from accident into policy.

## Decision

**D1 — `tailscale serve` (tailnet-private) is THE documented remote-access path.** Rationale: end-to-end encryption (WireGuard between devices; the Let's Encrypt cert's private key never leaves the box), zero inbound ports / CGNAT-proof, ACL-governed and identity-attributable, `--bg` config survives reboots, and the 2026 free Personal plan (6 users, unlimited devices, serve+certs+MagicDNS included, "free forever") covers a self-hoster with headroom. No surveyed alternative matches it on E2E + credential surface + 15-minute setup simultaneously.

**D2 — Exposure is narrowed to the designed-for-remote surfaces; admin protection must never depend on a side effect.** The blessed serve config is safe-by-construction:
- **Ingest:** a path-scoped mount — `tailscale serve --bg --https=8443 --set-path=/api/ingest http://127.0.0.1:8787/api/ingest` — so the tailnet sees ONLY the ingest route (per-connection secret; constant-time; fail-closed). This retires the current whole-edge `:8443→8787` mapping, under which the admin class was shielded only by serve's Host-header passthrough hitting the loopback allowlist (verified working today — `GET /api/agents` over tailnet → 403 — but it is a rebinding-guard side effect, not a designed boundary, and it also exposed the Console SPA shell to every tailnet peer).
- **MCP:** whole-port is fine — `tailscale serve --bg --https=10000 http://127.0.0.1:8788` serves only `/mcp` (bearer 401 before any tool; everything else 404s by construction).
- **Read mirror (optional, advanced):** a third mount set for the five bearer-gated read paths may be added the same way for non-MCP harnesses; documented but not default.
- **Invariants (binding):** the tailnet hostname goes in `REST_ALLOWED_HOSTS` **never**; any fronting proxy MUST forward the original Host header; the post-deploy checklist gains a probe — an admin route over the tailnet must 403/404. These hold even if someone reverts to a whole-edge mapping.

**D3 — Funnel is an explicit, warned, opt-in fallback — never the default.** Funnel makes the port public-internet-reachable (anonymous, no ACLs, undisclosed bandwidth caps); for a box holding finance/health/mail it is only justified when a specific consumer needs public reachability. **Hazard (recorded):** serve and Funnel are last-command-wins on the same port, and our 8443/10000 are two of Funnel's three eligible ports — one mistyped `tailscale funnel` silently publishes a private endpoint. **Hardening (recommended default):** remove the `funnel` node attribute from the tailnet policy (deny `autogroup:member`), making Funnel impossible without a deliberate admin-console change.

**D4 — Honest client-coverage matrix (what this story can and cannot promise).** Tailnet-private + static bearer covers every LOCALLY-RUNNING harness today: Claude Code (`--header "Authorization: Bearer …"`), Cursor (`mcp.json` headers — works precisely because we serve no OAuth well-knowns; a known Cursor bug ignores headers when OAuth discovery exists, tracked before we ever add PRM endpoints), Claude Desktop via the `mcp-remote` stdio bridge, IDEs. NOT covered — these connect from vendor clouds and can never reach a tailnet: claude.ai/Desktop remote connectors (GA path is OAuth; static "Request headers" is beta-gated), ChatGPT consumer connectors (OAuth 2.1 only, no static-token path at all), Anthropic/OpenAI server-side API connectors (accept static bearers but require public HTTPS). Those need Funnel (D3) plus, for the strict ones, the OAuth 2.1 resource-server work — which stays where it is: **deferred to Release-wave R**, unchanged by this ADR. (Niche note: OpenAI's Secure MCP Tunnel reaches private servers outbound-only, but routes through OpenAI's channel — custody posture makes it a user's call, not our recommendation.)

**D5 — Tailscale is the recommendation, not a hard dependency.** The gateway itself only ever binds loopback; ANY carrier of HTTPS-to-loopback works. The documented alternatives tier (for the runbook, weighted for no-third-party-plaintext and setup time): **LAN-only** (privacy-max, no remote) · **Tailscale serve** (the default) · **Pangolin on a ~$5 VPS** (no-Tailscale self-hosted tunnel; TLS on your VPS) · **port-forward + Caddy on-box** (expert-only; CGNAT-check first; public 443 on a home IP is internet-scanned within the hour). **Rejected as the default: Cloudflare Tunnel** — architecturally terminates TLS at Cloudflare's edge and reads request plaintext; disqualifying for finance/health/mail content regardless of its excellent ergonomics. **Escape hatch:** Headscale (active, v0.29.x) replaces the coordination server if Tailscale-the-company ever must be exited — with the recorded caveat that serve-with-HTTPS is an open Headscale gap (their #1921) and Funnel is not planned; a coordination-server outage meanwhile does NOT break existing tunnels (data plane is independent).

**D6 — macOS headless caveat (ties to the owed auto-login ops item).** Only the open-source `tailscaled` variant runs pre-login; the GUI variants join the tailnet only after a user session starts. The runbook records: for a fully unattended box, either enable auto-login or migrate to the `tailscaled` LaunchDaemon. (Which variant a given box runs is a checklist item.)

## Consequences / follow-ups

- Runbook: the deployment runbook gains the D2 blessed config + the tailnet-403 probe in the post-deploy checklist; a new self-hoster-facing `docs/runbooks/remote-access.md` carries the D5 tier + Funnel recipe with warnings; existing deployments migrate from the whole-edge `:8443` mapping to the path-scoped mount (config-only, reversible).
- Filed, not blockers (Release-wave R edge hardening, pre-existing): agent bearers have no expiry; no rate limiting on any edge; a revoked bearer's cached MCP session survives until its next initialize. Exposure via serve does not worsen these, but public exposure via Funnel would — the Funnel recipe references them as prerequisites for anything beyond a demo.
- CT-log note for the privacy-conscious: enabling tailnet HTTPS publishes machine names to Certificate Transparency logs — name the node blandly (documented in the runbook).
- The repo's working notes gain one clause: remote access = tailscale serve per this ADR.

**Postscript 2026-07-17 (mcp-auth-bridge, ADR 0029):** "only /mcp exists; everything else 404s by construction" is now qualified — when the opt-in OAuth bridge is enabled (`MCP_PUBLIC_URL` set), the MCP edge additionally serves the bridge routes (`/.well-known/*`, `/register`, `/authorize`, `/token`). Bridge OFF (default) = the sentence holds byte-for-byte. The bridge is how strict hosted clients (claude.ai/ChatGPT) authenticate; they still require the deliberate Funnel opt-in to REACH the edge — this ADR's exposure tiering is unchanged.

**Postscript 2026-07-21 (live-matrix finding — cloud MCP connectors need port 443, D3's `:10000` Funnel CANNOT reach them):** The #47 live matrix confirmed the bridge's full server-side OAuth contract over the tailnet, then hit a hard wall on the actual claude.ai/ChatGPT connect: **their connector backends egress on port 443 ONLY — a non-443 port (the blessed Funnel recipe uses `:10000`) gets a silent TCP reset before any request leaves the vendor's network** (claude.ai: "Couldn't reach", `ofid_…`, zero requests at our edge, public DNS routable; corroborated by the Claude connectors troubleshooting docs' "non-443 port" cause). So D3/D4's "Funnel makes strict hosted clients work" is now **port-qualified: the Funnel must be on `:443`, not `:10000`** (Tailscale Funnel supports 443/8443/10000; only 443 reaches cloud connectors). Tailscale Funnel on `:443` stays privacy-clean (TLS terminates at the node, D5's whole reason Cloudflare was rejected) — so the fix is to free `:443` for the MCP edge, NOT to adopt Cloudflare (which would read the finance/health/mail plaintext the bridge carries — D5 still binds). Runbook §OAuth bridge corrected. Anthropic's outbound-only MCP tunnels are a claude.ai-only zero-inbound alternative (same custody caveat as OpenAI's, D4's niche note). Tracked in #47 (bridge = verified; the live cloud-client cell is pending a `:443` endpoint).

**Postscript 2026-07-25 (the 443 citation is wrong; the finding is not — U3 `the-443-endpoint`, ADR 0035):** The 2026-07-21 postscript above closes its evidence list with the clause *"corroborated by the Claude connectors troubleshooting docs' "non-443 port" cause"*. **That citation is not supportable and is withdrawn: Anthropic documents no port restriction on connector egress, anywhere.** A future agent who goes looking for that doc will not find it, and finding nothing is exactly how a real finding gets discarded along with its bad footnote — so the correction is recorded rather than the sentence silently trusted.

**What survives, unchanged:** the *finding* is real. It rests on this repo's own controlled experiment of 2026-07-21 (#47: claude.ai reported "Couldn't reach" with an `ofid_…`, **zero** requests reached our edge, and public DNS for the name was routable — i.e. the reset happened before anything left the vendor's network), and it is independently reported by practitioners in the same terms. **What it is not is a published vendor contract.** It is an observed behaviour of someone else's infrastructure, undocumented by them, and it **may change without notice in either direction** — a non-443 port may start working, or the observation may stop reproducing. Anything that depends on it (the `:443` Funnel recipe, the port map) should be re-probed rather than assumed, and dated when it is.

**Two of this ADR's own decisions are also superseded, recorded here so a reader of §D3 does not act on a retired stance:** ADR 0035 §D1 supersedes §D3's "explicit, warned, opt-in fallback" framing — public exposure on `:443` is now a first-class supported configuration with a runbook recipe, though still never a default (ADR 0035 §D2). ADR 0035 §D8 rescopes §D3's hardening recommendation: **scope** the `funnel` node attribute to the gateway node's tag rather than **deny** it to `autogroup:member`, because denial would now deny the supported configuration. §D2's invariants (the tailnet hostname goes in `REST_ALLOWED_HOSTS` never; a fronting proxy must forward the original Host header) and §D5's rejection of Cloudflare are UNCHANGED and still bind.
